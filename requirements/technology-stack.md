# Технологический стек

## Контекст

`Real City` - браузерная multiplayer-стратегия в реальном времени на одной общей постоянной карте. Сервер должен быть авторитетным источником истины для состояния карты, строительства, экономики, боев, поведения монстров, владения объектами, таймеров и проверки действий игроков.

Игра использует изометрическую подачу. Модели объектов создаются в Blender, а затем размещаются на игровой карте как изометрические ассеты.

## Основной стек

### Frontend

- Язык: TypeScript.
- Фреймворк приложения: React.
- Сборщик: Vite.
- Основной рендерер: PixiJS.
- Клиентское UI-состояние: Zustand или Jotai.
- Запросы к серверу вне realtime-обновлений: TanStack Query.
- Realtime-транспорт: WebSocket.
- Стилизация: CSS Modules, Tailwind CSS или обычный CSS с дизайн-токенами.

PixiJS выбран как предпочтительный рендерер основной карты, потому что игра представляет собой изометрический 2D/2.5D стратегический интерфейс с большим количеством спрайтов, оверлеев, состояний выбора и инкрементальных обновлений карты. Three.js можно использовать для вторичных 3D-превью, инспекции ассетов или внутренних инструментов, но не как основной рендерер игровой карты.

### Backend

- Язык: Go.
- База данных: PostgreSQL.
- Кэш и временное состояние: Redis.
- Realtime-шлюз: WebSocket.
- Фоновая симуляция: Go workers или внутренние сервисы.
- Миграции базы данных: Goose, Atlas или другой Go-friendly инструмент миграций.

Go выбран для бэкенда, потому что игре нужна стабильная авторитетная симуляция, эффективная realtime-сеть, явная доменная логика и предсказуемые долгоживущие серверные процессы.

## Ответственность бэкенда

Бэкенд является авторитетным источником для:

- состояния карты;
- занятости тайлов;
- владения зданиями и жизненного цикла зданий;
- ресурсных узлов и производства ресурсов;
- инвентарей игроков;
- таймеров строительства;
- перемещения и времени пути;
- расчета боев;
- рейдов и разрушений;
- AI монстров;
- правил территории и защиты;
- cooldown'ов;
- проверки всех действий игроков;
- генерации событий для клиентов.

Клиенты отрисовывают состояние и запрашивают действия. Им нельзя доверять итоговые координаты, владение объектами, стоимость действий, завершение cooldown'ов, значения урона, награды или валидность действий.

## Realtime-архитектура

Для live-событий игрового процесса используются WebSocket-соединения:

- обновления видимых объектов карты;
- начало, завершение и отмена строительства;
- изменения ресурсных узлов;
- боевые события;
- перемещение и атаки монстров;
- изменения территории;
- чат;
- уведомления;
- присутствие игроков.

Обновления карты должны быть инкрементальными. Сервер должен отправлять изменения по релевантным чанкам или видимым областям, а не пересылать весь мир при каждом изменении.

## Архитектура карты и рендера

Клиентская карта строится вокруг изометрической PixiJS-сцены с отдельными слоями рендера:

- terrain;
- roads and walls;
- buildings and resource nodes;
- units and monsters;
- effects;
- selection overlays;
- territory overlays;
- hover and placement previews;
- debug overlays for development.

Карта должна поддерживать:

- перемещение камеры;
- zoom;
- загрузку по чанкам;
- выбор объектов;
- hover тайлов;
- предпросмотр размещения;
- сортировку глубины по изометрической позиции;
- стабильные anchors объектов;
- инкрементальные обновления по событиям сервера.

## Пайплайн ассетов

Объекты моделируются в Blender и экспортируются в игровые изометрические ассеты.

Рекомендуемый пайплайн:

1. Создать модель объекта в Blender.
2. Отрендерить ее из фиксированной изометрической камеры.
3. Экспортировать основной спрайт.
4. Экспортировать дополнительные состояния, если нужны:
   - строительство;
   - поврежденное состояние;
   - руины;
   - улучшенный вариант;
   - кадры idle-анимации.
5. Экспортировать спрайт тени, если нужен.
6. Упаковать спрайты в texture atlases.
7. Сгенерировать JSON-метаданные для размещения и рендера.

Рекомендуемые поля метаданных:

```ts
type ObjectVisualDef = {
  id: string
  atlas: string
  frame: string
  footprint: { w: number; h: number }
  anchor: { x: number; y: number }
  sortOffset: number
  shadowFrame?: string
  states: {
    normal: string
    construction?: string
    damaged?: string
    ruined?: string
  }
}
```

Так игровая логика остается независимой от заменяемых визуальных ассетов.

## Доменная модель

Ключевые игровые концепции должны быть явно представлены в backend-коде:

- Map;
- Chunk;
- Tile;
- Building;
- ResourceNode;
- Player;
- Group или Faction;
- Monster;
- Action;
- Combat;
- Inventory;
- Territory;
- Event.

Доменные правила по возможности должны быть тестируемыми до подключения к persistence, networking и UI.

## Рекомендуемый первый MVP

Первый технический milestone должен доказать работу общей карты и server-authoritative flow:

1. Изометрическая карта на PixiJS.
2. Перемещение камеры и zoom.
3. Загрузка чанков.
4. Несколько типов terrain-тайлов.
5. Размещение зданий с проверкой footprint.
6. Выбор объекта и панель деталей.
7. Ресурсные узлы.
8. Серверная валидация строительства.
9. WebSocket-события для обновлений карты.
10. Одно простое поведение roaming monster как проверка симуляции.

После этого можно расширяться в производственные цепочки, рейды, стены, территории, группы, рынки и более глубокие PvE/PvP-системы.
