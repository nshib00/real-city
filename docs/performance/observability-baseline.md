# Базовая линия наблюдаемости

## Локальный серверный прогон 16.10.2026

Изолированный Compose project `real-city-observability`: API со встроенной симуляцией, Postgres 16, Redis 7, Prometheus 3.15.0. Пустая БД с миграциями по `000023_observability_queue_indexes.sql`; API на `127.0.0.1:18081`, Prometheus на `127.0.0.1:19090`. Хост: Linux/WSL, AMD Ryzen 5 5500U. Окружение является разработческим, без игрового браузера и конкурентных игроков. Не переносить эти числа на production.

Повторить HTTP-прогон после запуска API можно командой `python3 scripts/record-observability-baseline.py --base-url http://127.0.0.1:8080 --seconds 30`. Скрипт печатает JSON по каждому сценарию с точными UTC-окнами. Перед повтором отметить, пустая БД или прогретая: повтор на той же БД уже не измеряет холодное создание чанков.

| Сценарий | Окно UTC | Запросов/ошибок | Клиентский p50/p95/max |
|---|---|---:|---:|
| Обычный viewport: `x=0,y=0,radius=16`, 1 поток, 30 с | 13:42:06–13:42:37 | 134 / 0 | 19,07 / 27,2 / 605,31 мс |
| Смешанный: два viewport `radius=48` и два `/world/chunks?radius=1`, 4 потока, 30 с | 13:42:37–13:43:07 | 436 / 0 | 37,56 / 63,52 / 1873,07 мс |

Клиентское время измерено Python `urllib` от начала запроса до прочтения полного тела. В первом обращении создаются чанки, поэтому максимум включает холодный старт; p95 ниже максимума. Смешанный сценарий чередовал `viewport (0,0)`, `viewport (80,40)`, `chunks (0,0)`, `chunks (2,1)` и паузу 200 мс между пакетами. Это проверка базовой работоспособности сигналов и грубый ориентир, а не воспроизведение полной карты из аудита.

На 13:43:00 UTC Prometheus показал `up=1` для API и Prometheus, HTTP histogram p95 `GET /api/v1/world/viewport` 88,2 мс за скользящую минуту, DB p95 `world.find_chunks` 9,25 мс, `world.copy_tiles` 242,5 мс, `building.viewport_list` 2,44 мс, scheduled tick p95 482 мс, pool wait 0, WS drops 0. Эта минутная выборка пересекает оба сценария и не является отдельным p95 смешанного сценария; гистограмма дает приближенный квантиль. Серии 5xx в выборке отсутствовали, что согласуется с 570 ответами 200. После прогона API экспортировал 463 samples за scrape; `prometheus_tsdb_head_series` показывал 1289 серий всего, включая Prometheus. Эти числа относятся к короткому прогону без игроков и не дают основания уменьшать retention.

Экспорт `/metrics` на этом хосте при одном уже зарегистрированном HTTP route: `BenchmarkMetricsExposition-12` — 849103 нс/операцию, 840836 Б/операцию, 1454 аллокации/операцию. Бенчмарк включает сбор `runtime.MemStats` и запись в `httptest.ResponseRecorder`, поэтому это верхнеуровневая стоимость локального scrape, а не overhead каждого игрового запроса. При интервале scrape 15 с ориентировочная доля одного CPU для такого scrape составляет около 0,006%; при росте числа серий повторить бенчмарк. HTTP middleware добавляет блокировку и обновление histogram на каждый запрос; его отдельная стоимость здесь не измерена.

## Что еще нужно измерить для окончательных порогов

- Desktop и реальное mobile устройство: три повторения `?perf=buildings`, `?perf=monsters`, `?perf=mixed` и обычной карты по [протоколу браузерного профилирования](browser-profiling.md). Зафиксировать FPS, frame p50/p95, heap/GC, Pixi children/cache/churn и Chrome trace с версией сборки.
- Реалистичная база с количеством построек, монстров и игроков из аудита; отдельно холодный и прогретый cache, placement, action/outbox backlog, `ws` fan-out. Сопоставить одинаковые UTC окна клиента и Grafana.
- Пересчитать число серий, стоимость scrape, p95/p99 HTTP/DB/tick и ошибки при длительном прогоне; только затем скорректировать buckets, scrape interval, retention и пороги `alerts.yml`.

Текущие buckets покрывают наблюдавшиеся p95 (HTTP 5–5000 мс, DB 1–5000 мс), поэтому по короткому локальному прогону менять их нет оснований. Интервал 15 с и retention 7 суток/2 GB остаются исходными настройками до прогона с реалистичным числом серий и проверки занимаемого диска. Первичные алерты сохранены без новых численных поправок, поскольку пороги пока не проверены реальной игровой нагрузкой.
