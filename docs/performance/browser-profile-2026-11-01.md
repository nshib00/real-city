# Браузерный профиль интерфейса — 01.11.2026

## Прогон

Автоматический smoke в Chromium, viewport 1440×900, DPR 1, с реальными React/Pixi и ассетами фронтенда. API и WebSocket изолированы фикстурами `mockInterfaceWorld`. Для карты использован dev-сценарий `?perf=mixed&perfBuildings=100&perfMonsters=30&perfResources=50&perfTileRadius=16`. Это локальный синтетический прогон, а не замер production или устройства игрока.

Результат снят `browser-review.spec.ts`, тест «профиль карты: загрузка, кадры, реакция на действие и перекрытие UI». Команда:

```sh
npm run test:ui-review -- --project=1440-dpr1 -g 'профиль карты'
```

## Результаты

| Метрика | Результат | Как измеряется |
|---|---:|---|
| До готового canvas и HUD | 1 923 мс | От начала `page.goto` до видимых canvas и performance HUD; API отвечает фикстурами |
| CSS, шрифты и изображения | 128 784 байта, 67 ответов | Размер тел ответов браузера без HTTP-сжатия; включает видимые в сценарии UI и графические файлы |
| Кадры | 56,8 FPS; p50 16 мс; p95 17 мс | 5 секунд `requestAnimationFrame` после появления карты; это интервал кадров, не CPU-время рендера |
| Реакция карты на увеличение | 124 мс | От запуска Playwright click до изменения CSS transform карты, зафиксированного `MutationObserver` |
| Закрытая интерфейсом площадь карты | 49,68% | Объединение пересечений видимой области карты с прямоугольниками панели ресурсов, инструментов, инспектора, событий, навигации и статусов |

Перекрытие вычисляется геометрически: прозрачность и реальная видимость карты под панелями не учитываются, поэтому это верхняя оценка занятой площади. Длительность реакции включает доставку клика через браузерную автоматизацию. Для оценки пользовательской задержки на физическом устройстве нужен независимый прогон.

## Сопоставление и ограничения

В [аудите производительности](performance-audit.md#повторные-измерения) зафиксированы сравнимые до/после размеры production `dist/assets` и главного JS после недавних оптимизаций: 959,11 → 812,21 МиБ для всей поставки, 492,02 → 468,78 КБ для главного JS. Там же записаны предыдущие браузерные frame samples. Они сняты в другой сессии/с другим состоянием графики и не являются A/B-парой для этого dev-прогона; вывод об улучшении FPS по ним не делается.

Для завершения пункта 8.5 нужно повторить тот же замер на production-сборке и реальном мобильном устройстве, выполнить по три прогона после прогрева и сохранить traces. Для строгого сравнения «до/после» требуются checkout старой версии и тот же браузер, GPU, viewport, набор ассетов и сценарий действий. В текущем окружении такой парный mobile/production прогон не проводился.
