# Профилирование карты в браузере

## Назначение и ограничения

Сценарии `?perf=buildings`, `?perf=monsters`, `?perf=mixed` доступны только в dev-сборке. Они создают фиксированные по количеству объекты в памяти клиента и заменяют ими отрисовываемые здания, ресурсы, монстров и тайлы. Поэтому они измеряют рендер и взаимодействие с картой; задержку реального API и WebSocket нужно измерять отдельно на обычной карте в том же окружении. Синтетические объекты не сохраняются на сервере.

Dev HUD показывает FPS и p50/p95 интервала между кадрами за последние 1,5 секунды, видимые объекты, число прямых children двух Pixi-контейнеров, размеры четырех retained caches, создания/удаления Pixi-объектов во время последнего полного redraw и доступную браузеру оценку JS heap. Интервал между кадрами включает простой, планирование и работу браузера; это не CPU-время функции рендера. Счетчики redraw не включают отдельные вызовы анимации между redraw. `heap n/a` означает, что браузер не предоставляет `performance.memory`. При размонтировании последнего PixiStage накопленные значения сбрасываются.

## Одинаковый прогон на desktop и mobile

1. Запустить фронтенд в dev-режиме и открыть карту с `?perf=buildings`, затем повторить с `?perf=monsters` и `?perf=mixed`. Значения по умолчанию: buildings — 2600 построек/160 монстров; monsters — 360/720; mixed — 2600/720; каждый сценарий содержит 260 ресурсов и радиус тайлов 34. Параметры `perfBuildings`, `perfMonsters`, `perfResources`, `perfTileRadius` позволяют изменить нагрузку; записать полный URL. Не смешивать результаты разных параметров.
2. Desktop: зафиксировать браузер и версию, ОС, CPU/GPU, разрешение окна, DPR, zoom карты, настройки энергосбережения и версию сборки/commit. Mobile: дополнительно модель, ОС, состояние питания и температуру/троттлинг, если доступны. Использовать реальное устройство; эмулятор Chrome пометить отдельно.
3. Закрыть лишние вкладки, подождать загрузки текстур, затем сделать warm-up 30 секунд: один проход pan по области и zoom туда-обратно. После warm-up вернуть камеру и zoom в начальное положение.
4. Записать 60 секунд покоя, 60 секунд непрерывного pan по одинаковой траектории и 60 секунд zoom между одинаковыми границами. Для каждого этапа снять Chrome DevTools Performance trace с Screenshots и Memory, FPS/frame timeline, длинные кадры, JS heap и GC; при доступности включить WebGL/Graphics показатели. Сохранить trace с названием `дата-устройство-сценарий-этап-повтор`.
5. Повторить полный прогон три раза на каждом устройстве и сценарии. Между повторами перезагрузить страницу и повторить warm-up. Снимать HUD в начале и конце каждого этапа и отметить максимум p95/children/cache/redraw churn. Для финальной оценки использовать медиану трех прогонов; показывать также разброс.

Проверить вкладку Memory на устойчивый рост heap после возвращения камеры и GC. При pan retained cache может временно расти; после возврата в ту же область число children/cache должно стабилизироваться. Если FPS падает при стабильных children/cache, смотреть main thread, GC и GPU в trace.

## Сопоставление с сервером и протокол baseline

Для обычной карты, без `?perf=...`, записать точное время начала и конца каждого этапа в UTC и тот же интервал выставить в Grafana. Сохранить скриншоты «Обзор производительности» и «API и карта» с `job`/`instance`: HTTP p95/p99 нужного route, DB operation p95, pool wait, HTTP 5xx, WS drops/очередь. Указать число HTTP запросов и WS событий за окно. Синтетический `?perf` прогон можно сопоставить по времени с графиками фона, но его искусственные объекты не создают эквивалентную нагрузку API/DB.

| Поле протокола | Значение |
|---|---|
| Дата и окно UTC, окружение, commit/build | Заполняется перед прогоном |
| Сценарий и полный URL, этап, повтор | `buildings` / `monsters` / `mixed` / обычная карта; покой / pan / zoom; 1–3 |
| Устройство, браузер, экран/DPR, zoom, режим питания | Заполняется перед прогоном |
| HUD: FPS, frame p50/p95, heap, видимые объекты | Значения и единицы для каждого этапа |
| HUD: Pixi children, retained caches, redraw +/− | Значения в начале/конце и максимум |
| Chrome Performance/Memory | Ссылка на trace; длинные кадры, GC/heap, GPU/WebGL при доступности |
| Grafana за то же окно | Ссылки/скриншоты; HTTP/DB p95, pool wait, 5xx, WS drops и объем событий |
| Вывод | Рендер/main thread, GC/heap, сеть, API/DB, WS либо неясно; подтверждение trace/графиком |

Если кадры тормозят при нормальных HTTP/DB/WS и длинных задачах main thread — исследовать рендер. Если паузы следуют за долгими запросами при нормальном кадре после ответа — исследовать сеть/API/DB. Если повторяются WS drops или большие очереди отправки — отдельно проверить доставку обновлений. Это диагностические признаки, а не доказательство причинности: для вывода нужен trace конкретного прогона.

Локальные серверные замеры записаны в [базовой линии наблюдаемости](observability-baseline.md). Браузерные числа здесь не подставлены: для них нужен отдельный прогон на desktop и реальном mobile устройстве по описанному выше протоколу. Исходный `httptest` срез `/metrics` из каталога не заменяет нагрузочную базовую линию.

## Клиентская телеметрия для staging

На текущем этапе staging-прием не включается: нет согласованной потребности в агрегатных данных и политики хранения. Если появится потребность, применять явный opt-in и фиксированную долю сессий, ограниченную частоту отправки агрегатов (например, одно окно 60 секунд), серверный endpoint с аутентификацией, проверкой диапазонов и размера тела. Передавать только тип устройства/класс viewport из конечного словаря, сценарий из конечного словаря, FPS/frame time/heap и количества объектов; исключить ID игрока, URL, координаты, IP в payload и произвольные labels. На сервере агрегировать по конечным категориям и экспортировать через собственный Prometheus registry. Браузер не пишет в Prometheus напрямую. До проектирования retention и контроля доступа хранить данные только локально в trace/HUD.
