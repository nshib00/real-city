# Доставка событий симуляции из отдельного worker в WebSocket API

## Проблема

При `SIMULATION_EMBEDDED=true` симуляция, `EventBus`, dispatcher outbox и WebSocket gateway работают в процессе API. События симуляции попадают в локальный `EventBus`, который читает gateway.

При `SIMULATION_EMBEDDED=false` симуляция запускается в отдельном `cmd/worker`. Он создаёт собственный `EventBus`, а gateway в `cmd/api` слушает другой экземпляр в другом процессе. Публикация в памяти worker не может достичь WebSocket-подключений API. Это касается, в частности, изменения построек, ресурсов, инвентаря, производства и монстров. Клиент увидит новое состояние только после повторного запроса/переподключения, если такой запрос произойдёт.

Есть второй путь потери: отдельный worker запускает `OutboxDispatcher`, который выбирает записи из общей таблицы `outbox_events`, публикует их в собственный `EventBus` и помечает как `sent`. В таком случае API больше не увидит запись. При этом в рабочем коде нет производителей `outbox_events` (запись использовалась в тесте): сама таблица и dispatcher не превращают прямые публикации `EventBus.Publish` в межпроцессные события.

## Причина и границы

- `backend/internal/service/eventbus.go` хранит подписчиков только в памяти процесса.
- `backend/cmd/worker/main.go` создаёт отдельный bus и dispatcher.
- `backend/cmd/api/app.go` создаёт bus для gateway, но запускает dispatcher только при встроенной симуляции.
- `backend/internal/worker/outbox_dispatcher.go` считает успешной публикацию в локальный bus, даже если за пределами процесса нет получателя.
- Outbox и WebSocket не обеспечивают подтверждение прочтения клиентом. После передачи gateway дальнейшая доставка клиенту остаётся best effort; при переподключении клиент должен перечитать состояние мира.

## Решение для текущего этапа

Оставить PostgreSQL общей точкой обмена, без отдельного брокера:

1. В режиме отдельного worker записывать каждое событие его `EventBus` в `outbox_events` с уникальным ID, типом, каналами маршрутизации, временем и сериализованным payload. Запись синхронна: событие не считается опубликованным, если append завершился ошибкой.
2. Не запускать `OutboxDispatcher` в отдельном worker. Запускать его в API независимо от `SIMULATION_EMBEDDED`, чтобы только процесс с WebSocket gateway выбирал и отмечал записи.
3. При чтении восстанавливать типизированный payload перед передачей gateway: он преобразует доменные структуры в публичные DTO, и формат сообщений клиенту должен оставаться прежним.
4. Для режима отдельных процессов требовать доступную общую PostgreSQL: fallback на независимые in-memory репозитории создаёт ложное впечатление работающей симуляции.
5. Проверить путь worker bus → outbox → API dispatcher → API bus, а также отсутствие dispatcher в worker и сохранение формата WebSocket payload.
6. Периодически удалять отправленные записи старше часа пакетами, сохраняя ожидающие и dead-letter записи для повторов и диагностики.

Запись события после изменения игрового состояния пока не выполняется в той же транзакции. При сбое между ними возможно изменение без realtime-события. Это ограничение существующих сервисных методов, которые вызывают `Publish` после записи; полную атомарность нужно вводить вместе с транзакционной переработкой конкретных игровых операций. Для WebSocket состояние PostgreSQL остаётся источником истины, клиент при восстановлении соединения перечитывает его.

## Критерии готовности

- Событие, опубликованное worker при `SIMULATION_EMBEDDED=false`, появляется в общем outbox и затем в `EventBus` API.
- Только API помечает outbox-событие как отправленное; отдельный worker не забирает его.
- Для событий построек и монстров WebSocket payload сохраняет публичный формат DTO.
- Ошибка записи в outbox видна в логах и не маскируется локальной публикацией.
- При отсутствии общей PostgreSQL отдельные процессы завершаются с ошибкой запуска.
- Отправленные записи удаляются по сроку хранения; pending и dead-letter записи очистка не затрагивает.

## Когда пересмотреть решение

Измерить возраст самого старого ожидающего события, число повторов, длительность dispatch и нагрузку на PostgreSQL при реалистичном числе игроков. Брокер имеет смысл выбирать при устойчивом backlog либо при нескольких API-инстансах: один dispatcher с `SKIP LOCKED` доставляет событие только одному API-инстансу. На текущем этапе это решение рассчитано на один API и один отдельный worker.
