### Где Redis-кэш есть и где он оправдан

**Внедрённых мест Redis-кэша: нет.** Контейнер Redis работает, но нулевые `keyspace_hits`/`keyspace_misses` и код подключения подтверждают, что API и worker не используют его для чтений. Мест с доказанной в текущем контуре выгодой Redis-кэша также нет. Realtime fan-out между несколькими API остаётся потенциальным применением Redis, но это транспорт событий, а не кэш; текущая схема с одним API не требует его.

| Данные | Частота изменений и допустимая задержка отображения | Решение по TTL и кэшу |
|---|---|---|
| Чанки мира | Terrain может измениться после действий игрока; старый tile и версия ETag вводят клиента в заблуждение. Авторитетные проверки требуют свежего состояния. | Redis не добавлять поверх текущих 100% warm hits. Для будущего общего кэша нужен DB version или инвалидация **после commit** и исправление локального cache в других процессах. TTL до 1 с может быть лишь страховкой для отображения, не механизмом согласованности; для принятия действий TTL = 0. |

Если нагрузка подтвердится: ключ `market:open:{limit}` с нормализованным limit, TTL **1 с**, инвалидация после commit каждого изменения ордера. Матчинг всегда читает PostgreSQL. |

| Здания и AI spatial reads | HP, состояние, проходимость и позиции меняются в ходе тиков и боя; устаревшая цель опасна для логики. | Не кэшировать между тиками. Существующий внутритиковый cache живёт один tick; авторитетные эффекты читают актуальную БД. |

Для возможного будущего read-through необходимы метрики `hit/miss`, latency Redis, ошибки, размер ключей и evictions, а также fallback в PostgreSQL при отказе Redis. Максимальный объём следует ограничить по фактическим размерам сериализованных значений и числу горячих ключей, а не задавать произвольное количество. Проверка writer A / reader B обязательна перед включением общего кэша. Сейчас расширение Redis-клиента и эти метрики не вводились, потому что cache path не был выбран.

## Краткий вывод

Ниже сохранён исходный статический анализ ревизии `8cd15312d352c4820d152302b583e32b0dbceb4b`. Текущие runtime-результаты и решение приведены в разделе выше; прежние приоритеты остаются гипотезами для другого масштаба нагрузки.

На ревизии `8cd15312d352c4820d152302b583e32b0dbceb4b` Redis **не участвует в обработке запросов backend** и не ускоряет ни один сценарий приложения. Redis-сервер запускается Compose, проходит healthcheck и передаётся через переменную `REDIS_ADDR`, однако API и worker не читают Redis-конфигурацию, не создают клиента и не передают его сервисам или адаптерам.

Есть пакет `internal/adapter/redis`, но это заготовка, а не действующий Redis-адаптер: клиент умеет подключиться и выполнить `PING`; `SessionStore` сохраняет данные в `memory.SessionStore`; `IdempotencyStore` хранит записи в локальной Go map. Операций `GET`/`SET`/TTL, пула соединений, pub/sub и Redis-кэша в пакете нет.

Кэширование в проекте уже существует на других уровнях:

- PostgreSQL `WorldRepo` держит до 1024 чанков мира в локальной памяти конкретного процесса и патчит его при локальном изменении тайла.
- Симуляция держит карты чанков и зданий только на время одного AI-типа/тика, чтобы делить пространственные чтения между монстрами.
- HTTP endpoint мира формирует ETag из координат и версий чанков; при совпадении `If-None-Match` возвращает `304`, но сначала всё равно получает данные через сервис/репозиторий.
- Клиентская часть использует TanStack Query и polling, а realtime WebSocket обновляет часть данных. Это клиентское кэширование и сокращение повторной передачи, не Redis.

Redis потенциально полезен прежде всего как **общий между несколькими API/worker процессами кэш изменяемых чтений и транспорт invalidation/realtime**. Для авторитетного игрового состояния, проверок разрешений и атомарных операций кэш не должен заменять PostgreSQL.

## Что именно сейчас делает Redis

### Запуск и конфигурация

Compose определяет Redis 7 и персистентный volume в локальной и production конфигурации. В production backend ждёт `redis: healthy`, а backend environment получает `REDIS_ADDR`. `backend/pkg/config/config.go` также читает `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`. Это подтверждает наличие инфраструктурного намерения, но не рабочее подключение приложения.

### Неподключённые заготовки

`internal/adapter/redis/client.go` открывает одно TCP соединение, умеет `AUTH`, `SELECT`, `PING` и формирует имена ключей. При этом отсутствуют команды хранения/чтения и TTL. Одно соединение хранится в одном `Client`; очереди/пула и синхронизации конкурентного доступа нет, поэтому даже добавление параллельных команд в текущую реализацию не было бы готовым безопасным клиентом.

`SessionStore` с Redis именем игнорирует аргумент `*Client` и делегирует все операции `memory.SessionStore`. `IdempotencyStore` не принимает `Client`, держит `map[string]...` под mutex и имеет TTL только как проверку/поле времени в памяти. Оба хранилища теряют совместное состояние между экземплярами процесса и рестартами. Они не доказывают, что пользовательские сессии или idempotency responses находятся в Redis.

Интеграционный тест с Testcontainers создаёт Redis и вызывает `Ping`; он проверяет достижимость сервера, а не кэширование или хранение данных приложением. Тест `internal/adapter/redis/integration_test.go` также ожидает явный `TEST_REDIS_ADDR`.

### Реальные текущие аналоги кэширования

| Механизм | Где живёт | Что ускоряет/сокращает | Время жизни и согласованность |
|---|---|---|---|
| Кэш чанков | `postgres.WorldRepo.cache` | Повторное чтение уже загруженного чанка мира не делает SQL lookup | Ограничение 1024 записи; при достижении лимита map сбрасывается целиком; локальные обновления патчат кэш; другой API/worker процесс кэш не инвалидирует |

## Где Redis мог бы ускорить backend

Оценки ниже — **гипотезы для измерения**, а не утверждение, что Redis уже нужен. Реальная выгода зависит от профиля нагрузки, числа backend процессов, размеров наборов, индексов, latency PostgreSQL/Redis и доли повторных чтений. Сначала нужно снять baseline метрик и SQL нагрузки.

### Приоритет 1: общий кэш чанков мира для нескольких API процессов

Путь чтения: `GET /api/v1/world/chunks` или `/api/v1/world/viewport` → `WorldHandler` → `WorldService.ListChunks/LoadViewport` → `WorldRepo.GetOrCreateChunks` → локальный cache lookup, затем PostgreSQL `findChunks`, затем при отсутствии — создание чанков и генерация.

**Потенциальный выигрыш:** если одни и те же чанки часто запрашиваются разными клиентами и API экземплярами, Redis может сократить повторные чтения `world_chunks` и тайлов, и разделить warm cache между репликами. Пользовательский viewport ограничен радиусом, однако при радиусе до 96 tiles service преобразует его в chunk radius до 3; наборы чтения ограничены, но карта может повторно запрашиваться часто.

**Ограничение уже имеющегося решения:** локальный кэш Postgres adapter покрывает повторные чтения того же процесса. Для одиночного API Redis добавит сетевой hop и сериализацию, поэтому может оказаться медленнее текущей памяти. ETag уменьшает сетевой payload, но handler всё равно загружает chunks для вычисления версии; общий Redis может помочь именно этой внутренней части, только если PostgreSQL чтения остаются существенными.

**Ключевая сложность:** чанки изменяемы. `UpdateTile` обновляет версию и патчит только локальный кэш. Отдельный worker, второй API экземпляр или другой mutation path могут изменить БД, оставив Redis/локальные копии старыми. Нужны транзакционно корректная стратегия публикации обновлений, версия чанка, инвалидирование/обновление после commit и поведение при отказе Redis. Не заполнять кэш значением из незавершённой транзакции. На cache miss для ещё не созданного чанка возможны конкурентные генерация/создание — базу всё равно нужно считать арбитром.

**Рекомендуемая форма:** ключ `world:{mapID}:chunk:{x}:{y}:v{version}` или версионирование по надежному DB version; сначала считать актуальную версию, затем брать payload по версии. Альтернатива — короткий TTL + надежная invalidation после commit, но один TTL создаёт окно устаревшего игрового состояния. Не кэшировать сырые auth-зависимые ответы viewport, если они различаются владельцем/правами.

### Приоритет 1 при горизонтальном масштабировании: realtime fan-out между процессами

Сейчас `EventBus` и WebSocket gateway создаются внутри каждого процесса. Outbox позволяет фиксировать события рядом с PostgreSQL транзакциями и dispatcher публикует события в локальную шину. При нескольких API репликах WebSocket клиент, присоединённый к процессу B, не обязан получить событие, опубликованное локально процессом A. Клиентский polling в `IsoMap.tsx` и компонентах снижает последствия задержки, но периодические чтения остаются.

Redis Pub/Sub или Streams могут разнести события между процессами и сократить задержку/зависимость от polling. Это **межпроцессная доставка**, не кэш. Pub/Sub может терять сообщения при отключённом подписчике; для важных событий нужно сохранять outbox как источник истины, а клиентам обеспечивать переподключение, cursor/replay или восстановление через API. Не считать Redis единственным хранилищем критичных событий.

### Приоритет 2: общие справочники и баланс игры

Баланс, каталог зданий/ресурсов и параметры симуляции являются кандидатами на кэш, если они запрашиваются часто и читаются из БД/дорогого вычисления. В текущем коде следует сначала проверить фактический путь: `domain/catalog` передаёт каталог как кодовые данные; создание приложения грузит его из пакета, а миграции содержат версию баланса. Такой неизменяемый набор обычно быстрее/проще держать в Go памяти, чем в Redis. Если впоследствии баланс станет динамическим из БД или будет обновляться без рестарта, Redis может раздавать версионированный общий snapshot нескольким процессам. Пока нет подтверждённого горячего SQL пути, Redis для статического каталога не обоснован.

### Приоритет 2: профильные агрегаты и списки, читаемые часто

`PlayerService` и social/economy adapters собирают профиль, здания игрока, состав альянса/бафы, инвентарь, список открытых market orders, сообщения чата, уведомления/threats. Frontend опрашивает некоторые данные каждые 5–15 секунд и реже при подключённом realtime: например inventory — 5s, production jobs — 5s, alliance profile — 10s, threats — 12s, chat — 15s или 60s, карта — 5–8s либо 30s в зависимости от WebSocket.

Кэшировать можно только конкретные **read models** с приемлемой задержкой устаревания:

- Публичные/полупубличные списки открытых market orders: частые одинаковые чтения; короткий TTL либо invalidation при создании/изменении/исполнении заказа. Не кэшировать результат выбора встречного ордера при исполнении: это блокирующая транзакционная логика.
- Профиль и агрегаты альянса: короткий TTL/version key; инвалидировать при изменении членства, treasury, уровня/бафа, помощи территории. Проверки членства/прав и разрешение действия всегда выполнять авторитетно.
- Список зданий для отображения/инспектора или пространственные выборки: потенциально дорого на загруженной карте и повторяется у соседних клиентов. При этом все изменения HP, состояния, footprint, владельца и удаления должны обновлять версию соответствующей области. Кэшировать целые `ListByMap` массивы рискованно из-за размера; предпочтительнее viewport/chunk projection с ограниченным объёмом.
- Результаты чата: быстрые новые сообщения уже могут идти realtime; история может кэшироваться коротко на канал/страницу, но private/nearby/alliance содержимое требует полного ключа области доступа и пользователя. Сообщения, флаги модерации и курсоры быстро изменяются; риск утечки между пользователями выше возможной выгоды.
- Сводки для панели угроз/уведомлений: повторные подсчёты кандидаты только после подтверждения дорогих запросов. Персональные результаты должны быть изолированы ключом пользователя и обновляться событиями.

**Решение:** не включать эти кэши “про запас”. Сначала измерить частоту, p95 и стоимость SQL, затем выбрать один конкретный read path.

### Приоритет 3: пространственное чтение зданий в AI между тиками

Внутритиковый `tickBuildingCache` уже убирает повторное чтение одинаковых chunk buckets между близкими монстрами. Межтиковый/общий cache мог бы сократить запросы `ListIntersectingFootprint`, если много монстров часто пересчитывают одинаковые области.

Однако AI использует эти данные для выбора целей, маршрута, угроз и взаимодействия с изменяемыми зданиями. Устаревший occupancy может вести к ошибочному пути или выбору уже уничтоженного/перемещённого объекта. Изменения от API, worker и боевых эффектов должны согласованно инвалидировать области; перед применением урона, trap charges и иных эффектов всё равно нужна свежая авторитетная проверка. До метрик безопаснее оптимизировать SQL/индексы и сохранить кэш на один tick.

### Приоритет 3: геометрия/terrain, если перестанет быть статичной

Сгенерированные чанки могут быть дорогими при первом создании, но затем уже сохранены PostgreSQL и попадают в локальный cache. Redis не заменит первичное создание, а для одиночного процесса, вероятно, не ускорит горячий memory-hit. Общий кэш имеет смысл только при множестве API реплик и повторяемом чтении одних и тех же неизменяемых terrain-данных. Изменяемые тайлы (лес, ресурсные объекты, версии) нельзя смешивать с immutable terrain без раздельных слоёв и инвалидации.

### Инфраструктурные сценарии, которые не являются кэшированием

- **Sessions:** распределённое хранилище может пригодиться, если backend должен масштабироваться и сессии сейчас лежат в локальной памяти. Но текущий API при Postgres использует `postgres.SessionRepo`, то есть сессии уже общие и постоянные. JWT access проверяется отдельным механизмом, а активность/отзыв сессии — отдельными проверками; перевод в Redis требует сохранить отзыв, TTL, refresh-token hash и поведение при сбое. Для надёжности PostgreSQL может быть подходящим источником истины.
- **Idempotency:** текущий Postgres store обеспечивает общий state, TTL, advisory lock и reservation между процессами. Замена на Redis возможна как ускорение middleware, но атомарные fingerprint/reservation/lock и срок хранения должны остаться корректными между репликами. Для денежной/игровой мутации потеря idempotency опаснее добавленной задержки. Скорее не кэш-кандидат, пока профилирование не выявит узкое место.
- **Rate limiting / distributed locks:** подходящие возможности Redis для будущего общего лимитера или распределённой координации, но доказательств действующего rate-limit через Redis нет; simulation locks и транзакционные правила сейчас основаны на PostgreSQL.
- **Очереди/Outbox:** Redis Streams мог бы быть транспортом при явном решении, но существующий Postgres outbox обеспечивает durable очередь. Простая замена на Pub/Sub ослабит надёжность.

## Где Redis использовать нельзя как источник истины

Не отвечать из кэша на решения, которые должны отражать текущее состояние мира и быть атомарными: баланс инвентаря при списании/начислении, покупка/исполнение market order, владение и членство/права, постройка и коллизии, HP/уничтожение, захват или добыча ресурса, cooldown/таймеры, idempotency reservation, выбор цели и применение combat эффекта. Эти операции используют транзакции, блокировки, условные обновления или ограничения PostgreSQL. Кэш можно использовать для предварительного отображения; конечная серверная проверка остаётся на БД.

## Как выбрать, что внедрять первым

1. Снять baseline по HTTP route, SQL query fingerprint, cache hit/miss, p50/p95/p99, числу запросов и числу активных API/worker реплик. Наблюдать отдельно обычный viewport, быстрые poll endpoints, AI ticks и нагрузку после mutations.
2. Проверить индексы и query plans прежде, чем добавлять кэш: Redis не исправляет full scan, неудачную пагинацию, чрезмерное число запросов или крупный ответ.
3. Для выбранного чтения определить: допустимое окно устаревания, точные ключи и права видимости, размер/TTL, invalidation события после commit, поведение при недоступности Redis и максимальный объём памяти.
4. Начать с read-through cache, где промах безопасно обслуживается PostgreSQL, Redis остаётся необязательной оптимизацией, а на запись кэш обновляется/инвалидируется только после commit.
5. Добавить метрики hit/miss/eviction/latency/error и сравнить с baseline. Если hit ratio низок или Redis hop дороже SQL, убрать кэш.
6. Проверить несколько процессов и конкурентную запись: writer A обновляет мир, reader B не должен бесконечно видеть старую версию; сбой Redis не должен менять авторитетное состояние игры.

## Рекомендуемый порядок кандидатов

| Очередь | Сценарий | Почему | Основной риск | Предварительная оценка |
|---|---|---|---|---|
| 1 | Межпроцессная доставка realtime-событий | Снижает задержку обновления WebSocket при горизонтальном масштабировании | Потеря Pub/Sub сообщений; нужен outbox/replay | Высокая ценность при >1 API процесса; это не cache |
| 2 | Общий кэш world chunks | Часто повторяется в viewport, уже есть локальный кэш и версии | Согласованность чанка и тайлов после всех путей записи | Наиболее естественный cache кандидат для нескольких API реплик |
| 3 | Короткий cache market read list / public read model | Polling и одинаковые чтения несколькими клиентами | Быстро меняющиеся записи; не кэшировать матчинг/сделку | Только если DB/SQL метрики показывают заметную нагрузку |
| 4 | Кэш профиля/альянса/агрегатов | Повторные панельные запросы и несколько SQL чтений | Изоляция доступа, много путей инвалидации | Средняя ценность, умеренно высокая сложность |
| 5 | Пространственные building reads между AI ticks | Возможное повторное чтение одних областей | Устаревшие цели/проходимость и межпроцессная инвалидация | Сначала измерить; внутритиковая оптимизация уже есть |
| 6 | Inventory, chat/private history, auth/session | Высокая частота отдельных чтений | Авторитетность, приватность, отзыв/atomicity | Не начинать с этих данных |

## Практическая карта чтения

Читайте источники в таком порядке:

1. `backend/cmd/api/app.go` — какие реализации реально подключены.
2. `backend/cmd/worker/main.go` — отдельный runtime симуляции и его зависимости.
3. `backend/pkg/config/config.go` — Redis параметры существуют, но сами по себе ничего не подключают.
4. `backend/internal/adapter/redis/client.go`, `session_store.go`, `idempotency_store.go` — фактические возможности и ограничения Redis-заготовок.
5. `backend/internal/adapter/postgres/world_repo.go` и `backend/internal/service/world.go` — основной cacheable путь загрузки мира и существующий локальный кэш.
6. `backend/internal/adapter/http/handler/world.go` — ETag и ответ viewport.
7. `backend/internal/worker/simulation/monster_ai.go`, `monster_building_cache.go` — текущий кэш AI в пределах тика.
8. `backend/internal/adapter/postgres/idempotency_store.go`, `session_repo.go` — уже действующие распределённые Postgres хранилища.
9. `frontend/src/game/IsoMap.tsx`, `frontend/src/features/economy/useInventory.ts`, `frontend/src/features/chat/useChatChannels.ts` — частоты повторного опроса и участие realtime.

## Вопросы для проверки модели

1. Если пользователь с тем же viewport попадёт на другой API процесс, какой текущий кэш он сможет повторно использовать? Ответ: только кэш этого нового процесса, если он уже был прогрет; Redis в текущем пути не участвует.
2. Если worker изменил тайл чанка, как API узнает, что его собственная локальная копия устарела? Сейчас это не гарантируется локальным `patchCachedTile`, который обновляет только кэш текущего `WorldRepo`; нужен межпроцессный механизм или стратегия проверки версии.
3. Почему нельзя кэшировать результат `GetInventory` и списывать ресурсы по нему? Потому что чтение для UI можно временно кэшировать при доказанной пользе, но списание должно быть атомарно проверено и применено на авторитетном хранилище.
