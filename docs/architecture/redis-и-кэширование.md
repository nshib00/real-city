# Redis и кэширование в Real City

## Актуальный статус — 08.11.2026

Предыдущая версия документа утверждала, что Redis в backend не используется. Это устарело: с коммита `0a19b01` (`perf(world): cache chunks and coalesce events`, 03.11.2026) Redis подключён как общий L2-кэш чанков мира.

Что верно сейчас:

- Redis включается только при наличии PostgreSQL и `REDIS_ADDR`: `backend/cmd/api/app.go:74-76`.
- Кэшируются чанки мира с TTL **2 секунды**: `backend/internal/service/world.go:89-133` и `162-207`, ключ `real-city:cache:chunk:{chunkID}` (`backend/internal/service/cache_keys.go:5-8`).
- Инвалидация идёт по событиям мира через WebSocket gateway: `backend/internal/adapter/ws/gateway.go:53-56` и `250-255`.
- Реализация команд `GET`/`SET PX`/`DEL`/`MGET` находится в `backend/internal/adapter/redis/game_cache.go`, а не в `client.go`.
- `redis.SessionStore` и `redis.IdempotencyStore` по-прежнему не используют Redis: первый делегирует в `memory.SessionStore`, второй хранит данные в локальной Go map. Они нигде не подключены.
- Production Compose запускает **один** backend со встроенной симуляцией (`SIMULATION_EMBEDDED=true`) и передаёт `REDIS_ADDR=redis:6379` (`docker-compose.production.yml`). Несколько API-реплик в штатной конфигурации нет.
- Отдельного замера эффективности Redis-кэша (hit/miss, latency, сравнение с L1) после включения в документации не зафиксировано. Последняя базовая линия от 01.11.2026 измеряла только process-local кэш `WorldRepo`, когда Redis ещё не использовался. Поэтому выгода Redis на текущем контуре не доказана, а корректность при нескольких процессах не проверена.

## Что изменилось в Redis-адаптере

| Утверждение | Статус | Свидетельство |
|---|---|---|
| Redis-клиент умеет только `PING` | Устарело | `client.go` действительно ограничен `Dial`/`PING`, но рабочий путь использует `game_cache.go` с `GET`, `SET ... PX`, `DEL`, `MGET` |
| Redis-кэш не внедрён | Устарело | `app.go:74-76` создаёт `GameCache` и передаёт в `WorldService.SetCache` |
| `SessionStore` хранит сессии в Redis | Неверно | `session_store.go:15-17` игнорирует `*Client` и создаёт `memory.SessionStore` |
| `IdempotencyStore` хранит записи в Redis | Неверно | `idempotency_store.go:14-46` использует локальную map под mutex |
| Redis является источником истины | Неверно | PostgreSQL остаётся авторитетным; Redis только ускоряет чтение и при ошибке заменяется SQL |
| Несколько API используют общий кэш | Не подтверждено | В production один backend; межпроцессная инвалидация не реализована |

`GameCache` открывает отдельное соединение на каждую команду, без пула. Таймауты: 200 мс на dial, 500 мс на команду; после ошибки dial кэш на 5 секунд перестаёт пытаться подключиться и логирует предупреждение не чаще раза в 5 секунд. Это безопасный fallback, но на высоком QPS лишний TCP-handshake и сериализация могут сделать Redis медленнее локального L1.

## Где переход с in-memory на Redis действительно оправдан

Общее правило: Redis нужен, когда данные должны быть **общими для нескольких процессов** или переживать рестарт процесса. Для кэша, который живёт внутри одного процесса и уже даёт попадания, Redis обычно добавляет сетевой hop и сериализацию, а не ускоряет.

### 1. Чанки мира — уже переведены, но с оговорками

**Оправдано как L2, не как замена L1.** Чанки читаются часто, набор ключей ограничен, для отображения допустимо отставание около 2 секунд, а события изменения уже публикуются. Redis помогает при нескольких API-репликах, холодном старте и всплесках после рестарта.

**Почему не стоит убирать L1.** Замер 01.11.2026 на прогретом наборе дал 56 832 попадания и 0 промахов в process-local кэше. При одном API Redis-запрос на каждый чанк, скорее всего, будет медленнее L1. Текущая схема «L1 → Redis → PostgreSQL» разумна, если L1 остаётся маленьким и быстрым.

**Незакрытые риски:**

- **Устаревание L1 после промаха Redis.** Если отдельный worker изменил чанк в PostgreSQL, API получит событие через outbox и удалит ключ Redis, но `WorldRepo.cache` не узнает об изменении. Следующий запрос промахнётся по Redis и обслужит устаревший L1. При встроенной симуляции это не проявляется, потому что `UpdateTile` патчит локальный кэш; при отдельном worker или второй API-реплике это реальный дефект. Перед таким запуском нужно либо отключать L1 при включённом Redis, либо задавать L1 короткий TTL не больше Redis TTL, либо проверять версию чанка в PostgreSQL.
- **Инвалидация только внутри процесса.** `InvalidateEvent` вызывается из локальной шины событий. Вторая API-реплика не получит `DEL`, если не подписана на общий канал. До появления межпроцессной подписки TTL 2 секунды остаётся единственной границей устаревания.
- **Нет метрик Redis.** Нельзя отличить попадание L1, попадание Redis и чтение SQL. Перед настройкой TTL и оценкой пользы нужны счётчики hit/miss/error/latency и размер значений.
- **Соединение на команду.** Для роста QPS нужен пул соединений; текущая реализация рассчитана на умеренную нагрузку.
- **Stampede на холодном кэше.** Блокировки чанков локальны для процесса. Несколько реплик могут одновременно загрузить один чанк; при необходимости поможет `SET NX`-lock или jitter TTL, но это оптимизация, а не обязательное требование.

### 2. HTTP rate limiting — главный кандидат на Redis при нескольких API

`MemoryRateLimiter` хранит счётчики в процессе. При N репликах эффективный лимит становится примерно N × limit, а ключи `IP:method:prefix` не удаляются и могут неограниченно накапливаться. Это уже не кэш, а общее состояние, для которого Redis подходит лучше:

- атомарный `INCR` + `EXPIRE` или Lua-скрипт со скользящим окном;
- общий ключ для всех реплик;
- локальный fallback fail-open, если Redis недоступен, чтобы не блокировать вход;
- метрики `allowed`/`blocked` по правилу.

**Решение:** переводить при появлении второй API-реплики. Для текущего одного backend срочности нет; полезно хотя бы ограничить рост map и добавить метрики.

### 3. Realtime fan-out и инвалидация — Redis Pub/Sub или Streams при нескольких API

Сейчас `EventBus` и WebSocket gateway живут внутри процесса. Outbox dispatcher выбирает события с блокировкой в PostgreSQL, поэтому каждая запись обрабатывается один раз, но публикуется только в локальную шину того процесса, который её забрал. Клиент на другой реплике не получит WebSocket-событие и будет ждать polling.

Redis Pub/Sub или Streams решают именно межпроцессную доставку. Это **не кэш**: outbox остаётся источником истины, Pub/Sub может терять сообщения при отключённом подписчике, поэтому нужны переподключение, cursor/replay или восстановление через API.

**Решение:** приоритет 1 при горизонтальном масштабировании; для одного процесса не требуется.

### 4. Read models рынка, профиля и альянса — только после профилирования

- Открытые ордера рынка: на пустой таблице индексный план занимал 0,116 мс. Кэшировать нечего, пока нет подтверждённой нагрузки.
- Профиль игрока и агрегаты альянса: несколько SQL-чтений и частый polling, но данные персональные и имеют много путей инвалидации. Допустим только display-only кэш с TTL 2–5 секунд и инвалидацией после commit; проверки прав и членства всегда идут в PostgreSQL.
- Списки зданий и пространственные проекции: потенциально дороги, но кэшировать целые ответы рискованно из-за размера; лучше ограниченные viewport/chunk-проекции.

**Решение:** не включать заранее. Сначала измерить p95 и стоимость SQL конкретного пути.

### 5. Сессии — не переносить

В production сессии уже лежат в PostgreSQL, то есть общие и переживают рестарт. Redis не даёт выигрыша, пока чтение сессии не станет заметной нагрузкой на PostgreSQL. При переносе пришлось бы сохранить отзыв, refresh-token hash, TTL и поведение при отказе Redis. Текущий `redis.SessionStore` — не реализация, а memory-fallback; его стоит либо удалить, либо явно пометить как заготовку.

### 6. Idempotency — не переносить

PostgreSQL-хранилище уже обеспечивает общий state, TTL, advisory lock и reservation между процессами. Потеря идемпотентности денежной или игровой мутации опаснее добавленной задержки. Redis можно использовать только как вторичный кэш готовых ответов, но не как авторитетный reservation.

### 7. Кэши симуляции — не переносить

`chunkCache` и `tickBuildingCache` живут один тик и используются для выбора цели, маршрута и проходимости. Сетевой запрос на каждый тик замедлит AI, а устаревшая occupancy приведёт к атаке по снесённой или перемещённой постройке. Перед уроном, ловушками и наградой всё равно нужны свежие проверки в PostgreSQL. Эти кэши должны оставаться в памяти.

### 8. Каталог и баланс — не переносить

Каталог зданий, ресурсов и параметров симуляции — статические данные Go, привязанные к версии приложения. Держать их в Redis бессмысленно: локальная память быстрее и не создаёт проблем согласованности.

### 9. Presence — уже в PostgreSQL

Фактическое присутствие игроков сохраняется через репозиторий и читается пространственным запросом. `service.PresenceService` с локальной map нигде не используется и не является рабочим хранилищем. Если позже появится высокочастотное online-состояние для WebSocket, Redis понадобится только при нескольких API; сейчас это не требуется.

### 10. HTTP-кэш ответов мира — оставить в памяти

Кэш хранит до 8 МиБ готового JSON на процесс, ключ включает версии чанков, поэтому он корректен и без инвалидации. Ответы viewport без сжатия достигали 1,15–3,21 МБ; дублировать их в Redis между репликами дорого по памяти и сети. Повторные запросы уже удешевляются ETag/304 и gzip на Caddy. Для нескольких реплик логичнее edge-кэш с учётом приватности, а не Redis.

## Что мерить перед следующим шагом

1. Добавить метрики Redis: `hit`, `miss`, `error`, `latency` по `GET`/`SET`/`DEL`/`MGET`, число evicted/expired ключей, размер значений и занимаемую память.
2. Сравнить на одном стенде три пути: L1 hit, Redis hit, SQL miss. Отдельно снять p50/p95/p99 и стоимость JSON-сериализации.
3. Повторить протокол 01.11.2026 после включения Redis: viewport, chunks, границы чанков, холодный и прогретый кэш.
4. Проверить сценарий writer A / reader B: отдельный worker меняет тайл, API должен перестать отдавать старую версию не дольше заданного окна.
5. Проверить отказ Redis: остановить контейнер и убедиться, что API продолжает обслуживать запросы через PostgreSQL без роста ошибок.
6. Для rate limit снять распределение 429 по репликам и проверить, что общий лимит не умножается на их число.

## Ограничения текущей реализации

- Redis не является источником истины. При ошибке `GameCache` возвращает ошибку, сервис логирует её и читает PostgreSQL.
- Ключи чанков имеют префикс `real-city:cache:chunk:`; тестовый контур использует `REDIS_DB=1`, production — `REDIS_DB=0`.
- TTL 2 секунды захардкожен в `world.go`; отдельной настройки нет.
- `client.go` и `game_cache.go` — два независимых клиента. `client.go` используется интеграционными тестами, рабочий кэш — `game_cache.go`.
- `redis.SessionStore` и `redis.IdempotencyStore` вводят в заблуждение названием пакета: первый является memory-fallback, второй — локальной map. Их не следует считать доказательством хранения сессий или идемпотентности в Redis.
- `service.PresenceService` не подключён; фактическое presence хранится в PostgreSQL.
- Межпроцессная инвалидация L1 и Redis не реализована. TTL 2 секунды ограничивает устаревание только для значений, которые действительно прошли через Redis; локальный L1 может оставаться старым дольше.

## Карта чтения

1. `backend/cmd/api/app.go` — какие адаптеры реально подключены, включая условие `db != nil && cfg.Redis.Addr != ""`.
2. `backend/internal/adapter/redis/game_cache.go` — рабочий Redis-клиент кэша.
3. `backend/internal/adapter/redis/client.go` — отдельный клиент для `PING` и интеграционных тестов.
4. `backend/internal/adapter/redis/session_store.go`, `idempotency_store.go` — незадействованные заготовки.
5. `backend/internal/service/world.go`, `cache_keys.go` — L2-кэш, TTL, ключи и инвалидация.
6. `backend/internal/adapter/postgres/world_repo.go` — L1-кэш на 1024 чанка и его локальный патч.
7. `backend/internal/adapter/http/handler/world.go`, `world_response_cache.go` — ETag, 304 и HTTP-кэш ответов.
8. `backend/internal/adapter/http/middleware/ratelimit.go` — process-local лимитер, главный кандидат на Redis при масштабировании.
9. `backend/internal/adapter/ws/gateway.go`, `connection.go` — локальная шина, подписки, инвалидация и лимит команд.
10. `backend/internal/worker/simulation/monster_ai.go`, `monster_building_cache.go` — кэши одного тика.
11. `backend/internal/adapter/postgres/idempotency_store.go`, `session_repo.go` — действующие общие хранилища PostgreSQL.
12. `backend/internal/observability/database.go` — метрики L1, а не Redis.

## Вопросы для проверки модели

1. Если игрок с тем же viewport попадёт на другую API-реплику, что он переиспользует? Redis-кэш чанков, если ключ ещё жив; L1 другой реплики — только если он уже прогрет. Межпроцессной инвалидации L1 нет.
2. Если отдельный worker изменил тайл, как API узнает об этом? Через outbox-событие API удалит ключ Redis, но его L1 останется старым. Это нужно исправить до запуска отдельного worker или второй реплики.
3. Почему нельзя полностью заменить L1 на Redis? На прогретом наборе L1 давал 100% попаданий без сети; Redis добавит dial, команду и JSON-сериализацию. Для одного процесса это вероятный регресс.
4. Почему нельзя кэшировать инвентарь и списывать ресурсы по кэшу? Потому что списание должно быть атомарным и авторитетным в PostgreSQL; кэш допустим только для отображения.
5. Где Redis действительно нужен в первую очередь? В общем rate limit и межпроцессной доставке событий при появлении второй API-реплики, а не в переносе локальных кэшей.
