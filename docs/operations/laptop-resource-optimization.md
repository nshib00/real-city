# Оптимизация тестового стенда для ноутбука

Дата: 31.10.2026. Оборудование: Ryzen 5 5500U, 8 ГБ RAM, одновременно открыт браузер. Ниже приведены анализ, предложения и статус первого этапа внедрения.

## Внедрённый режим ноутбука

Добавлен `docker-compose.laptop.yml` поверх тестового Compose с тем же project name `real-city-test`. Поэтому используются существующие тестовые тома БД и Redis. Режим запускает PostgreSQL, Redis, API со встроенной симуляцией и небольшой статический frontend через Caddy. Отдельный frontend-контейнер заменяет постоянно работающий Vite; число контейнеров само по себе не является целью.

Настроены квоты из таблицы ниже, ротация логов и уровень `info`; PostgreSQL получает указанные ниже настройки памяти и соединений. Для Caddy первоначально выделили 0,25 CPU, после измерения насыщения 01.11.2026 квоту повысили до **0,5 CPU**; лимит памяти — 128 МиБ. Интервалы симуляции/outbox и batch сохранены. Пул соединений API настраивается через `POSTGRES_MAX_OPEN_CONNS`/`POSTGRES_MAX_IDLE_CONNS`; в режиме ноутбука — 5/2, в обычном — 20/10.

В левой панели есть кнопка «Экономный режим карты». Она сохраняет выбор локально и сразу переключает карту между 30 FPS/DPR ≤ 1 и 60 FPS/исходным DPR. Переключение пересоздаёт Pixi canvas, поэтому возможно краткое мигание. В скрытой вкладке ticker карты останавливается и возобновляется при возвращении; сетевое состояние продолжает обновляться.

Запуск из корня проекта:

```bash
make laptop-config
make laptop-build
make laptop-up
```

Открыть `http://localhost:15173`. API сохраняет порт 18080. Сборка выполняется отдельным шагом, сервисы собираются последовательно; ограничение ресурсов BuildKit этим не гарантируется. Для установки новых изменений повторить build и up. Не запускать сборку параллельно с замером игры.

`laptop-up` сначала останавливает стандартные сервисы frontend/backend, поднимает хранилища, выполняет forward-миграции одноразовым контейнером и запускает API/frontend. Перед переключением остановить дополнительные API/worker, подключённые к той же базе. Контейнеры с нестандартными именами не останавливаются автоматически: их назначение ещё не подтверждено. `--remove-orphans` не используется, тома не удаляются.

Остановка и замер:

```bash
make laptop-stop
make laptop-measure
# Или заданная продолжительность (секунды):
bash scripts/measure-laptop-resources.sh 120
```

Скрипт измерения ничего не меняет; сохраняет поток Docker stats, vmstat, список процессов без аргументов и память до/после в отдельный каталог `/tmp/real-city-resources.*`. Требуются Docker, procps и GNU timeout; запускать в терминале хоста. При недоступном Docker скрипт завершится ошибкой. Для сравнения повторять одинаковую игровую сцену.

Возврат: `make laptop-stop`, затем прежние команды тестового стенда. До переключения проверить свободные порты и отсутствие другого API, подключённого к той же БД.

Проверки первого этапа: объединённая Compose-конфигурация валидна, имена прежних томов подтверждены; синтаксис shell, TypeScript и production-сборка с флагом экономии прошли. Два новых теста проверяют бюджеты рендера, скрытие/возвращение вкладки и удаление слушателя. В общей проверке frontend прошли 393 из 394 тестов (100 файлов прошли, один файл с ошибкой): `Inspector.test.tsx:177` ожидает `throwing_knives.svg`, но такой img не найден. Ошибка воспроизводится отдельным запуском теста; компонент инспектора этим этапом не изменялся.

На 01.11.2026 Docker доступен. Оба тестовых тома существуют. `real-city-design-check` отсутствует; `real-city-test-admin-world` — остановленный API из образа `real-city-test-backend:townhall15`. Сборка и запуск режима ноутбука успешны: `http://localhost:15173` и API `/ready` отвечают 200. В базе 2 пользователя. Миграции выполнены, `pg_stat_statements` включён в тестовой БД.

В 12-секундном замере работающего стенда **без открытой игры** Docker показал средний CPU: backend 13,0%, PostgreSQL 26,4%, Redis 0,8%, статический frontend 0,0%. Пики соответственно 15,1%, 37,0%, 3,6%, 0,3%. У API в момент профиля было 2 открытых соединения из лимита 5, ожиданий соединений не было. `vmstat` показывал 92–94% свободного CPU в конце окна и почти нулевой swap-in/out. Исходный лог: `/tmp/real-city-resources.nfCXBq`; профиль: `/tmp/real-city-profile.dTBsy9`.

Из 3,38 с суммарной длительности семи начальных тиков 3,07 с пришлись на стадию `monster_ai` (≈91%). `pg_stat_statements` после включения расширения зафиксировал, в частности, 1100 обновлений `monsters` (120,6 мс SQL), 3540 чтений `buildings` (88,7 мс SQL), 1298 чтений `monsters` (77,1 мс SQL), 1100 вставок `monster_events` (46,1 мс SQL). Это наблюдение за короткий промежуток, без активной игры; время Go включает больше, чем SQL. Крупнейший подтверждённый кандидат для следующей оптимизации — работа AI монстров и число запросов на одного монстра.

Замер нагрузки браузера при включённой/выключенной кнопке ещё нужен на ноутбуке с открытой игрой: Docker stats не измеряет вкладку. Время отклика действий, GPU-память и качество анимации после переключения также не измерены. Сравнивать нужно одинаковую сцену, последовательно переключая кнопку; использовать диспетчер задач браузера и `make laptop-measure`.

В отдельном девятисекундном измерении `vmstat` CPU был занят примерно на 53–76%, системная составляющая доходила до 36%, чтение swap — примерно до 30 МиБ/с, запись — до 96 МиБ/с. Занято около 5,6 ГиБ swap. Это подтверждает активную подкачку в момент измерения, но не устанавливает виновный процесс. Снимки Docker и vmstat сделаны не одновременно. Показанные контейнеры суммарно использовали около 436 МиБ по метрике Docker; это не полный учёт всей памяти хоста, браузера, файлового кеша и инфраструктуры Docker.

Из окружения агента Docker недоступен, а список процессов изолирован. Поэтому нет CPU-профилей, списка процессов контейнеров, планов SQL и измерения браузера. Ниже гипотезы отделены от подтверждённых фактов.

## Что обнаружено в проекте

- `docker-compose.test.yml`: PostgreSQL 16, Redis 7 и backend; лимитов CPU/RAM нет. Данные сохраняются в именованных томах.
- В проверенных Compose и скриптах нет определений `real-city-design-check` и `real-city-test-admin-world`. Их фактические команды, образы и происхождение нужно выяснить через Docker inspect. Нельзя считать `admin-world` обычным API без проверки.
- `backend/.env.example`: встроенная симуляция включена, тик 1 с, outbox 500 мс, batch 100, worker count 1, catch-up limit 10 минут, debug-логи.
- `backend/internal/worker/simulation/runner.go`: тик последовательно обрабатывает действия, постройки, производство, ресурсы, спавн и AI; есть метрики стадий и режим catch-up. Это точки для измерений, а не доказанные узкие места.
- `backend/internal/adapter/postgres/db.go`: пул жёстко ограничен 20 открытыми и 10 простаивающими соединениями на процесс.
- `docker-compose.dev.yml`: frontend при запуске выполняет `npm install` и запускает Vite. Это дополнительные затраты запуска и разработки.
- `backend/Dockerfile`: многостадийная сборка; во время работы используется готовый бинарник в Alpine, компилятор остаётся в build stage. Уже предусмотрены кеши сборки.
- `frontend/Dockerfile`: предусмотрена сборка frontend с раздачей через Caddy.
- `frontend/src/game/renderer/PixiStage.tsx`: DPR берётся без верхнего ограничения, ticker ограничен 60 FPS, на кадрах вызывается обновление монстров и оверлеев. Нужна оценка стоимости этих обновлений.
- Observability Compose добавляет Prometheus/Grafana; отдельный worker включается профилем. Для него предусмотрена проверка отключения встроенной симуляции.

## Варианты сокращения состава стенда

| Вариант | Ожидаемая польза | Ограничения и решение |
| --- | --- | --- |
| Останавливать `design-check` после проверки | Самый перспективный первый шаг по имеющемуся снимку CPU | Сначала определить команду и убедиться, что это завершённая/необязательная проверка. Сравнить до и после |
| Не запускать dev/test/production одновременно | Убирает дубли API, БД, симуляций и watchers | Проверять все Compose-проекты, а не только текущий файл |
| Проверки дизайна, E2E, генерацию ассетов запускать по требованию | Убирает постоянную нагрузку браузеров и генераторов, если они действительно есть | Оформить профилями или одноразовыми заданиями; при явном запуске сервиса профиль не мешает его старту |
| Один API со встроенной симуляцией | Три основных контейнера, без отдельного worker | Для локальной игры обычно достаточно; не дублировать симуляцию |
| Отдельный worker вместо встроенного | Помогает измерять и ограничивать симуляцию отдельно | Само по себе не уменьшает работу, добавляет процесс и пул БД; API должен иметь `SIMULATION_EMBEDDED=false` |
| Статический frontend вместо Vite | Убирает HMR, наблюдение за файлами и dev-преобразования | Нужна пересборка после изменений; удобно для игры и ручной приёмки |
| API/Vite на хосте, БД/Redis в Docker | Упрощает профилирование, иногда уменьшает расходы файловых монтирований | Работа приложения остаётся; на нативном Linux выигрыш от удаления контейнерной оболочки может быть небольшим |
| Удалить Redis | По замеру польза минимальна: менее 9 МиБ и 1% CPU | Сначала проверить зависимости сессий и realtime; не рекомендуется первым шагом |
| Удалить PostgreSQL/заменить in-memory хранилищем | Подходит для отдельных unit/UI-тестов | Не эквивалентно общей постоянной игре, транзакциям и SQL; не замена интеграционному стенду |
| Объединить все процессы в один контейнер | Сокращает число контейнеров визуально | Не устраняет вычисления и память процессов, ухудшает управление; не рекомендуется |
| Перенести API/БД на другой компьютер | Максимально разгружает ноутбук от серверной работы | Нужны другая машина и сеть; браузерный рендер остаётся локально |

Для остановки использовать `stop` или `down` без `-v`; удаление томов не является оптимизацией.

## Ограничения ресурсов и настройки процессов

Создать отдельный laptop override, сохранив обычный стенд для интеграционных проверок. Начальные экспериментальные бюджеты:

| Сервис | CPU-квота | Жёсткий предел RAM | Примечание |
| --- | ---: | ---: | --- |
| API со встроенной симуляцией | 1,5 | 768 МиБ | `GOMAXPROCS=2`, мягкий `GOMEMLIMIT=512MiB` |
| PostgreSQL | 0,75 | 768 МиБ | Проверить миграции и пиковые запросы |
| Redis | 0,25 | 192 МиБ | Следить за реальным размером данных |
| Одноразовые проверки | 1–2 | По измеренному пику | Не запускать одновременно с игрой на первом этапе |

Это предложения, не измеренные требования и не обещание расхода. Неиспользованный лимит не резервирует указанную память. Слишком низкий лимит вызывает OOM; CPU-квота может создавать очередь и задержки. `GOMAXPROCS` ограничивает параллельное исполнение Go, но не является квотой CPU. Проект использует Go 1.24: нельзя полагаться на поведение новых версий runtime по автоматическому учёту квот.

`GOMEMLIMIT` мягкий, не ограничивает всю память контейнера и требует запаса. Слишком низкое значение увеличивает частоту GC и расход CPU. Не менять `GOGC` без профиля: экономия RAM может стоить дополнительного CPU.

Дополнительно:

- Установить ротацию Docker-логов, сократить debug-логирование. При `info` сообщения начала/конца тика и некоторые сообщения AI всё ещё сохраняются; при необходимости сделать подробные успешные события debug или агрегировать их, сохранив ошибки.
- Настроить пул БД через конфигурацию; начать эксперимент с 5 открытыми и 2 простаивающими соединениями на API. Проверить ожидание пула, транзакции и наличие нескольких процессов. Простое снижение лимита не устраняет дорогие SQL.
- Для небольшой тестовой БД рассмотреть `shared_buffers=128MB`, `work_mem=4MB`, `maintenance_work_mem=64MB`, `max_connections=30`, `max_parallel_workers_per_gather=0`. Сначала узнать текущие значения: часть уже может совпадать с ними. Общий бюджет соединений должен учитывать API, worker, миграции и административный доступ. `work_mem` выделяется на операции, а не один раз на весь сервер.
- Не увеличивать кеш PostgreSQL, исходя из всех 8 ГБ: память нужна браузеру и ОС. Не отключать autovacuum, fsync или надёжность Redis ради обычной игры. Агрессивная eviction Redis может ломать используемые им данные; сначала определить их назначение.
- Healthcheck можно сделать реже, например 30 с, но ожидаемая экономия мала.

## Оптимизация серверной работы

1. Снять длительность стадий scheduled/catch-up, частоту catch-up на запросах, обработанные объекты и размер очереди. Проверить, не запускаются ли дорогие повторные проходы мира при частых HTTP-запросах.
2. Снять CPU/heap-профиль Go локально, если диагностический endpoint будет добавлен. Не предполагать, что pprof уже доступен; не открывать его публично.
3. Найти дорогие SQL через `pg_stat_statements` при доступном расширении либо временный порог логирования медленных запросов. Использовать планы выполнения и количество вызовов: много дешёвых запросов тоже дают нагрузку. `EXPLAIN ANALYZE` изменяющих запросов не запускать на сохраняемой базе без безопасной процедуры.
4. Проверить выборки монстров, спавнеров, территории, производства и ближайших объектов на полные проходы, N+1 и лишние обновления. Добавлять индексы по фактическим условиям/планам; пакетировать чтения и записи, не ослабляя блокировки и атомарность.
5. Обрабатывать только наступившие события, планировать следующую дату выполнения. Разделить частоты подсистем: бой, производство и housekeeping имеют разные требования. Изменять расписание с тестами времени и восстановления после простоя.
6. Дедуплицировать одинаковые запросы мира, ограничить размеры viewport/дельт, не рассылать неизменившиеся объекты. Проверить обёрнутые координаты и видимость игроков при любых пространственных оптимизациях.
7. Для UI-разработки предусмотреть компактный отдельный мир с контролируемыми числами объектов. Сохранить большой мир для нагрузки; текущую БД не очищать.

Увеличение тика с 1 до 2 с и outbox с 500 мс до 1 с может снизить частоту опросов, но ухудшить реакцию боя и доставки событий. Сначала проверить, что механики используют прошедшее время корректно. Уменьшение batch не гарантирует экономии: оно может создать растущую очередь. Отключение симуляции допустимо для изолированной проверки UI, но не для обычной игры.

## Браузер и frontend

| Мера | Эффект и проверка |
| --- | --- |
| Опциональные 30 FPS | Меньше кадров; отдельно проверить плавность камеры и ввод |
| Ограничение DPR до 1–1,5 | Меньше пикселей и памяти render targets; снижение чёткости. DPR 2 против 1 означает вчетверо больше пикселей |
| Остановка анимации скрытой вкладки | Исключить ненужную работу; после возврата восстановить актуальное состояние сервера |
| Перерисовка при изменениях | Разделить статичные слои и анимацию; проверять стоимость обходов/создания объектов каждый кадр |
| Ограничение текстурного кеша | Контролировать GPU/CPU-память после долгого перемещения по миру; не выгружать используемые общие текстуры |
| Атласы и подходящие размеры изображений | Меньше переключений и декодирования; оценивать размер декодированных данных, а не только WebP-файла |
| Ограничение истории и кешей | Проверить React Query, чат, события, WS и повторные подключения на неограниченный рост |
| Уменьшение фонового polling | Согласовать realtime-инвалидации, скрытые панели и вкладки; сохранить восстановление после потери WS |
| Закрытие диагностических окон | Сравнить с выключенными DevTools, инспекторами моделей и дополнительными игровыми вкладками |

Нужны профили Performance/Memory и диспетчер задач браузера. Проверить аппаратное ускорение: программный рендер может сильно увеличивать CPU. Не отключать GPU вслепую. Игровые настройки качества должны быть независимы от темы оформления.

## Сборка, ОС и другие варианты

- Не запускать сборки, E2E и генерацию ассетов параллельно с игровой сессией. Ограничить параллелизм сборки отдельно от runtime; runtime-квоты не гарантируют ограничение BuildKit.
- Повторно использовать готовые образы и кеши. Пересобирать только изменённые сервисы. Не выполнять `npm install` при каждом обычном старте; зависимости устанавливать отдельным шагом с lockfile.
- В Vite ограничить watch нужными каталогами, не включать polling файлов без необходимости. Для Playwright на ноутбуке начать с одного worker и одного браузера, не шести размеров одновременно.
- На Docker Desktop учитывать RAM виртуальной машины; на нативном Docker Linux такой VM может не быть. Не переносить настройки Desktop механически на текущую ОС.
- Закрыть лишние вкладки/IDE-процессы, сравнить их PSS/RSS с контейнерами. Не суммировать RSS процессов с общей памятью как точный физический расход.
- Zram или настройка swap могут смягчить дефицит, но компрессия тоже расходует CPU. Не отключать swap и не делать `swapoff` при дефиците RAM; не использовать очистку page cache как лечение.
- Проверить температуру, частоты и режим питания: троттлинг меняет время выполнения. Увеличение RAM, если модель ноутбука допускает, помогает многозадачности, но не исправляет горячий цикл CPU.
- Уменьшение размера Docker-образа и очистка неиспользуемых образов освобождают диск; это не равнозначно снижению runtime CPU/RAM.

## План измерений и порядок внедрения

1. Из терминала хоста получить `docker ps` и `docker inspect` двух нестандартных контейнеров. Смотреть образ, entrypoint, команду, restart policy, Compose labels и mounts; полный inspect может содержать секреты, не публиковать его целиком.
2. Снять 60 с базовой нагрузки: `docker stats`, `vmstat 1`, процессы хоста и браузера. Первый отчёт vmstat — среднее с загрузки ОС, его исключить из интервального сравнения. Записывать системный CPU, swap-in/out, доступную память и ошибки игры.
3. Повторить одинаковую сцену после остановки только `design-check`. Это отделит его вклад; выяснить, почему он продолжает работать и должен ли завершаться автоматически.
4. Повторить с закрытой игровой вкладкой и затем с открытой неподвижной картой. Сервер оставлять включённым. Сравнить браузер и контейнеры, не менять одновременно настройки.
5. Сравнить простой мира, активную игру и перемещение камеры; после прогрева текстур отдельно проверить 10–15 минут на рост памяти. Для UI-стенда сравнить Vite и статическую сборку.
6. Ввести laptop override и проверить не только CPU, но и задержки действий, backlog, длительность тика, ошибки/OOM и корректность данных. При троттлинге контейнера проверить `cpu.stat` cgroup.
7. Только затем оптимизировать подтверждённые горячие стадии Go/SQL/Pixi. Для временных и конкурентных изменений запускать соответствующие тесты; нагрузочные проверки делать отдельно.

Приоритет P0: определить и убрать ненужную постоянную проверку `design-check`, проверить процессы хоста и активный swap. P1: один стенд, ресурсные бюджеты, статический frontend для игры, экономный рендер. P2: профили и оптимизация SQL/симуляции/кешей. Перенос сервера и расширение RAM — альтернативы после оценки стоимости.

Критерии успеха: исчезновение устойчивой интенсивной подкачки в сопоставимой сцене, снижение среднего CPU/энергопотребления, отсутствие роста очередей и памяти, приемлемая отзывчивость. Процент улучшения заранее не установлен: текущих измерений для прогноза недостаточно.
