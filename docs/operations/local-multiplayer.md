# Совместная игра в локальной сети на текущем этапе

Проверено по исходникам 24 октября 2026 года. Это инструкция для нескольких устройств в одной домашней или офисной сети. Полный запуск на нескольких физических устройствах в рамках этой проверки не проводился: Docker daemon в текущем окружении недоступен для команды `docker info`.

## Ответ для двух устройств

**Да, достаточно одного backend и одного frontend на первом компьютере.** Второй компьютер или телефон ничего не запускает: он только открывает страницу в браузере. Оба браузера обращаются к одному frontend по адресу первого компьютера; Vite пересылает запросы API и WebSocket в тот же единственный backend.

```text
Устройство 1 (Windows + WSL)                  Устройство 2 (ПК или телефон)
PostgreSQL + один backend :8080               Только браузер
Один Vite frontend :5173                      http://<LAN_IP_УСТРОЙСТВА_1>:5173
Браузер: http://<LAN_IP_УСТРОЙСТВА_1>:5173
                 │                                         │
                 └──────── одна страница и один мир ──────┘
```

| Устройство | Что запустить | Что открыть в браузере |
| --- | --- | --- |
| Первое, где лежит проект | Backend, PostgreSQL и frontend, **по одному экземпляру** | `http://<LAN_IP_УСТРОЙСТВА_1>:5173` или `http://localhost:5173` |
| Второе, в той же сети | Ничего | `http://<LAN_IP_УСТРОЙСТВА_1>:5173` |

На втором устройстве **не нужны** копия проекта, Docker, отдельный backend или доступ к порту 8080. Для уверенной проверки сети удобно сначала открыть один и тот же LAN-адрес на обоих устройствах.

## Что уже работает по архитектуре

У всех игроков должен быть **один запущенный backend**, одна база PostgreSQL и один мир `dev-world`. Каждый человек открывает frontend в своём браузере и регистрирует отдельный аккаунт. Backend хранит игроков, карту и постройки в PostgreSQL, проверяет действия на сервере и рассылает события клиентам, подписанным на соответствующие чанки карты. Симуляция запускается внутри backend при `SIMULATION_EMBEDDED=true` (значение в `backend/.env.example`).

Сейчас доступны регистрация и вход, общая карта, строительство, экономика, монстры, чат, союзы и рынок. Постройки других игроков можно увидеть в видимой области карты: frontend отдельно запрашивает постройки текущего игрока и постройки видимого участка. Чат опрашивается раз в 5 секунд. Это пригодно для локальной проверки совместной игры, но не подтверждает готовность всех механик к полноценному публичному мультиплееру.

## Два препятствия в текущей конфигурации

1. **WebSocket через Vite не проксируется.** Клиент открывает `ws://<адрес-страницы>/api/v1/realtime`, а в `frontend/vite.config.ts` прокси `/api` задан как строка `http://localhost:8080`. Для установленной версии Vite проксирование upgrade-запросов включается только при `ws: true` либо при `ws:`/`wss:` в адресе target. HTTP API при этом может работать, но индикатор realtime будет переподключаться, а изменения карты на другом устройстве не будут приходить в реальном времени. Нужная минимальная правка:

   ```ts
   proxy: {
     '/api': { target: apiProxyTarget, ws: true },
   },
   ```

   После правки перезапустить Vite. Это предложение к изменению конфигурации; файл `vite.config.ts` данным документом не менялся.

2. **Frontend в Docker Compose указывает прокси не на тот контейнер.** `docker-compose.dev.yml` запускает frontend в отдельном контейнере, но не задаёт `VITE_API_PROXY_TARGET`. Поэтому его Vite обращается к `localhost:8080` *внутри frontend-контейнера*, где backend нет. Для варианта с frontend в Docker в сервис `frontend` нужно добавить:

   ```yaml
   environment:
     VITE_API_PROXY_TARGET: http://backend:8080
   ```

   При запуске frontend непосредственно в WSL и backend через опубликованный Docker-порт штатное значение `http://localhost:8080` подходит, если этот порт доступен из WSL.

## Рекомендуемый запуск: backend в Docker, frontend в WSL

1. **Только на устройстве 1** в корне проекта открыть терминал и выполнить `make backend-up`. Команда запускает PostgreSQL и Redis, применяет миграции и затем запускает **один** backend на опубликованном порту `8080`. Оставить терминал открытым. Использовать основной стек, не `make test-backend-up`: тестовый backend работает с отдельной базой и портом `18080`.
2. Проверить в WSL: `curl -f http://localhost:8080/health` и `curl -f http://localhost:8080/api/v1/world`. Первый адрес показывает, что HTTP сервер отвечает; второй проверяет доступность мира. Проверить в логах backend сообщение `postgres.connected`. Если PostgreSQL недоступен, backend **молча для пользователя переключается на хранение в памяти** и прогресс пропадёт после перезапуска. Одного `/health` для проверки базы недостаточно.
3. Внести показанную выше правку `ws: true` в `frontend/vite.config.ts`.
4. **Только на устройстве 1** в другом терминале выполнить `make frontend-dev`. Эта команда запускает **один** Vite на `0.0.0.0:5173`.
5. На Windows устройства 1 узнать его LAN IPv4 командой `ipconfig`. Найти адрес активного Wi-Fi или Ethernet адаптера, например `192.168.1.50`; не брать адрес WSL, Docker или виртуального адаптера. Открыть `http://192.168.1.50:5173` сначала на устройстве 1, затем на устройстве 2. Заменить адрес на фактический IP. Оба браузера используют **один и тот же frontend и один backend**.
6. На устройстве 2 ничего не запускать. В браузерах зарегистрировать отдельные аккаунты с разными email. Пароль в форме регистрации должен содержать минимум 10 символов. Чтобы увидеть друг друга на карте, открыть близкие области мира или договориться об одинаковых координатах: события карты рассылаются клиентам по подписке на видимые чанки.

Клиент использует относительные URL `/api/v1/...`, а WebSocket формирует из адреса открытой страницы. На втором устройстве запрос к `http://192.168.1.50:5173/api/v1/world`, например, приходит в Vite на устройстве 1, оттуда уходит в `localhost:8080` **на устройстве 1** и возвращается в браузер второго игрока. Поэтому на телефоне или втором ПК **не надо** указывать `localhost:8080` как адрес backend: для них `localhost` означает само устройство.

### Если страница не открывается с другого устройства

Codex запущен в Debian под WSL, а внешние устройства подключаются к Windows по его **LAN-адресу**. Указанный в `AGENTS.md` адрес `172.28.192.1` предназначен для обращения из WSL к приложениям Windows; это не адрес для других устройств. Проверьте, что оба устройства находятся в одной сети, не включена изоляция клиентов Wi-Fi, Vite слушает `0.0.0.0:5173`, а Windows Firewall пропускает входящий TCP 5173.

Если запуск из WSL доступен только на самом компьютере, настройте переадресацию TCP 5173 из Windows в WSL. В PowerShell от администратора, подставив актуальный IPv4 WSL из `wsl hostname -I`:

```powershell
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=5173 connectaddress=<WSL_IPV4> connectport=5173
New-NetFirewallRule -DisplayName "Real City LAN 5173" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5173 -Profile Private
```

Адрес WSL может измениться после перезапуска, тогда правило нужно обновить. Для предложенного варианта с Vite-прокси открывать порт 8080 другим устройствам не требуется. Если Docker Desktop уже публикует frontend-порт на Windows и адрес открывается, `portproxy` не нужен.

## Альтернатива: оба приложения в Docker Compose

После добавления `ws: true` в Vite и `VITE_API_PROXY_TARGET=http://backend:8080` в `docker-compose.dev.yml` можно запустить миграции и оба сервиса:

```bash
make migrate-up
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build backend frontend
```

Для игроков адрес такой же: `http://<LAN_IP_WINDOWS>:5173`. Если Docker-порт опубликован только локально или блокируется Windows Firewall, нужно разрешить TCP 5173 для частной сети. Порты PostgreSQL 5432 и Redis 6379 по текущему Compose тоже публикуются на хосте; для подключения игроков они не нужны.

## Что ограничивает совместную игру сейчас

- **Социальные данные хранятся в памяти.** `backend/cmd/api/app.go` всегда создаёт `memory.NewSocialRepo()` для чата, союзов и рынка, даже при доступном PostgreSQL. Данные этих функций теряются после перезапуска backend и не будут разделяться между несколькими процессами backend. Для локальной игры использовать один экземпляр API.
- **При сбое базы есть переход на память.** Это позволяет серверу продолжить работу, но после перезапуска исчезнут аккаунты и состояние мира, созданные в таком режиме. Перед игровой сессией проверять `postgres.connected` в логах.
- **Без WebSocket синхронизация неполная.** Отдельные экраны обновляются после собственных действий или периодическим опросом, но чужие изменения карты и постройки должны приходить через realtime. Текущую строковую настройку прокси нужно исправить до совместной игры с живым обновлением.
- **Сессии привязаны к браузеру.** Токены хранятся в `localStorage`. Разные устройства могут войти в разные аккаунты; для двух игроков в одном браузере удобнее отдельные профили или приватное окно.
- **Прямые набеги на игроков пока не реализованы.** Маршрут `GET /api/v1/raids` возвращает `status: "placeholder"`. Совместная сессия сейчас означает присутствие в одном мире и взаимодействие через существующие постройки, экономику и социальные функции, а не готовый PvP-цикл.
- **Это локальный dev-запуск.** Доступ извне домашней сети, публикация сайта и долговременная работа без присмотра здесь не настроены. Отдельная раздача `frontend/dist/` без HTTP/WebSocket-прокси не заменит Vite: клиент ожидает маршруты `/api/v1/...` на том же адресе, что и страница.

## Быстрая проверка двух игроков

1. На обоих устройствах открыть один и тот же LAN-адрес `http://<LAN_IP_УСТРОЙСТВА_1>:5173` и зарегистрировать по одному отдельному аккаунту. На устройстве 2 никаких серверов не запускать.
2. Убедиться, что оба клиента вошли, а индикатор realtime показывает подключение, а не переподключение. В инструментах браузера запрос `/api/v1/realtime` должен получить HTTP `101 Switching Protocols`.
3. Открыть близкую область карты на обоих устройствах. Разместить постройку первым игроком; второму она должна появиться без перезагрузки страницы. Проверить обратное направление.
4. Отправить сообщение в общий чат. На другом устройстве оно должно появиться в пределах примерно 5 секунд.
5. Перезапустить backend и войти снова: построенное при подключённом PostgreSQL должно сохраниться; сообщения чата, союзы и рынок сейчас не сохраняются.
