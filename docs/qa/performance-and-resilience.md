# Проверка нагрузки и восстановления

`scripts/measure-realtime.py --base-url http://127.0.0.1:18080 --connections 8 --seconds 30` измеряет доставку настоящего сообщения всем WS и проверяет переподключение. Токен задаётся через `REAL_CITY_ACCESS_TOKEN`. Скрипт изменяет глобальный чат тестового стенда, отправляя не более 30 сообщений в минуту. p95 включает HTTP-отправку и доставку клиенту, а не только серверную задержку.

`bash scripts/test-production-local.sh` использует отдельный Compose-проект и удаляет его volumes после проверки. Проверяются пауза/остановка PostgreSQL, остановка Redis, HTTP 503 при недоступной БД, инвентарь и повторный WS-вход. `REAL_CITY_ACCEPTANCE_ARTIFACTS` задаёт каталог логов и коротких HTTP/WS-отчётов; в CI это `artifacts/production`. Реальных результатов в текущем окружении нет; поиск узких мест и сравнение до/после ещё не выполнены.

Используйте отдельный тестовый сервер и копию данных; параметры мира и количество объектов должны соответствовать ожидаемому выпуску. Измерения пустой карты не подтверждают производительность населённого мира.

## HTTP-нагрузка

```bash
python3 scripts/record-observability-baseline.py --base-url http://127.0.0.1:18080 --seconds 30 --workers 8 --max-p95-ms 2000 --max-error-rate 0 > /tmp/real-city-load.jsonl
```

Прогон проверяет обычный viewport, смешанные запросы и чанки на швах мира. JSONL содержит количество запросов, HTTP-статусы, p50/p95/max, фактическое время, пропускную способность и долю ошибок. Превышение бюджета завершает процесс с кодом 1. При необходимости задайте токен через переменную `REAL_CITY_ACCESS_TOKEN`; скрипт его не печатает. Порог 2000 мс — начальный проверочный бюджет, который следует уточнить после первого воспроизводимого замера.

Сохраните вместе с отчётом revision кода, параметры CPU/RAM, размеры БД, число построек/монстров/игроков, состояние кеша, метрики PostgreSQL, длительность тиков и размер очереди. Повторяйте одинаковую нагрузку до и после оптимизации. Наличие индекса или кеша само по себе не доказывает улучшение.

## Реальное взаимодействие

`scripts/test-gameplay-local.sh` проверяет сохранение данных через рестарт API со встроенной симуляцией. Браузерный сценарий `frontend/tests/e2e/real-gameplay.spec.ts` обращается к настоящему API и ожидает WebSocket-дельты. Отдельные UI-сценарии используют HTTP-заглушки и служат проверкой интерфейса, а не multiplayer-приёмкой.

Для длительного браузерного замера включите существующий Performance HUD, используйте смешанный сценарий карты и двигайте камеру через шов не менее пяти минут. Измеряйте кадры, живые текстуры/объекты и память после возврата камеры. Автоматический HTTP-прогон не измеряет FPS, WebSocket fanout или стоимость тика.

## Сбои

На выделенном тестовом окружении отдельно проверьте разрыв сети браузера, перезапуск API, недоступность Redis и краткую остановку PostgreSQL. После восстановления повторите чтение инвентаря и карты, подтвердите отсутствие повторной оплаты/XP, догон фоновых задач и повторную подписку клиента. Не принимайте HTTP `/health` за подтверждение целостности игровых данных.

Клиент игнорирует повреждённые и несовместимые WebSocket-конверты и запрашивает повторную синхронизацию. Переподключения имеют случайный разброс задержки, чтобы клиенты не возвращались одновременно. Сохранение данных и поведение API при недоступной БД/Redis требуют отдельного запуска; в текущем окружении эти проверки не выполнены.

При заданном `POSTGRES_DSN` API отказывается запускаться, если соединение не установлено за 10 секунд. Автоматического переключения на пустую memory-базу больше нет. Production также требует непустой DSN. Это предотвращает запуск временного мира вместо сохранённого после сбоя PostgreSQL. Memory-режим остаётся доступен вне production только при явно пустом DSN.
