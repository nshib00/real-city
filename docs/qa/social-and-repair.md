# Приёмка социального контура, рынка и ремонта

Реализация добавлена 30.10.2026. Серверная приёмка требует Go 1.24+ и тестовой PostgreSQL с миграциями 000041 и 000042. В среде выполнения этой задачи Go отсутствует, Docker socket недоступен; живой прогон здесь не подтверждён.

## Социальные данные

При настроенной PostgreSQL API использует SocialRepo PostgreSQL для союзов, членства, приглашений, казны, баффов, помощи, сообщений и заявок рынка. Memory остаётся режимом без БД. Операции союза выполняются в UnitOfWork, изменение состава блокирует строку союза.

Участник может выйти. Лидер населённого союза сначала передаёт лидерство другому участнику; после передачи становится обычным участником. Последний лидер при выходе распускает союз и удаляет его зависимые данные. Лидер, заместитель и офицер исключают только строго нижестоящую роль; исключение самого себя выполняется через выход. Казначейство снимается при передаче лидерства и удалении членства.

Чат союза и личные события адресуются приватным каналам конкретных игроков, выбранных сервером. После исключения бывший участник не получает новые союзные сообщения и не читает историю через API. Клиент обновляет кеши по событиям и после reconnect; polling остаётся страховкой. События публикуются только после успешной транзакции. EventBus не заменяет долговечный журнал доставки: пропущенные сообщения восстанавливаются из истории БД.

Позиция прочтения хранится для игрока и канала; у союза scope содержит ID союза. PATCH /chat/read принимает только ID сообщения из доступной свежей истории. Позиция двигается монотонно; свои и помеченные модерацией сообщения не увеличивают unread. Открытый видимый канал отмечается прочитанным, другие показывают счётчики. У private/nearby остаются ограничения существующего MVP: полноценные отдельные диалоги и географическая фильтрация не закрываются этой задачей.

## Рынок

Резерв ресурсов/комиссия и запись заявки выполняются одной транзакцией. Отмена блокирует заявку, возвращает резерв и меняет статус в одной транзакции. Повторная отмена даёт Conflict и не возвращает ресурсы повторно. Комиссия не возвращается. Возврат ранее зарезервированных монет не обрезается изменившейся ёмкостью хранилища. Автоматическое сопоставление заявок остаётся пунктом 11.7.

Проверки: ошибка после SQL INSERT откатывает и заявку, и инвентарь; ошибка сохранения отмены откатывает возврат; две отмены одновременно дают один возврат. Для memory-адаптеров операции сериализуются и используют снимки для отката. Общий memorytx gate исключает параллельные обращения к затронутым репозиториям на время снимка, поэтому откат не стирает чужое конкурентное сообщение или изменение инвентаря.

## Ремонт

GET /buildings/{id}/repair показывает владельцу цену, рабочего, длительность и текущую работу. PATCH здания с action=repair запускает оплаченный серверный таймер. Цена — четверть материалов строительства текущего уровня пропорционально недостающему HP, с округлением каждого ненулевого материала вверх. Один рабочий резервируется до окончания. Время — половина пропорционального времени строительства, минимум пять секунд. Это начальная серверная политика баланса; UI не рассчитывает цену самостоятельно.

Повторный запуск блокируется. Завершение выполняет simulation worker, включая работу после перезапуска. Повреждённая выжившая постройка того же владельца, типа и уровня восстанавливается до максимального HP. При продаже, смене типа/уровня или разрушении работа отменяется: рабочий возвращается исходному игроку, материалы не возвращаются, чужой объект/руина не восстанавливаются. Восстановление руин остаётся отдельным действием. Рабочий возвращается ровно один раз; pending job сохраняется в PostgreSQL. Инспектор показывает стоимость и срок, population summary учитывает занятых ремонтников.
