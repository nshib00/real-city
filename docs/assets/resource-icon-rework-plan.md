# План переработки иконок ресурсов

## Цель и рамки

Заменить условные изображения предметными, материально узнаваемыми миниатюрами: камень с неровными плоскостями скола, древесина с корой и торцом, доски с плоским распилом и волокнами. Это реалистичность материала внутри яркой стилизованной диорамы Эолии, а не фотореализм или копирование чужих иконок. Сохранить исходные игровые ID, подписи, цены и компоновку интерфейса. Острые ребра сколов должны читаться, но иметь узкую фаску для блика; органику и жидкость не превращать в каменные кристаллы.

Источники истины: `shared/catalog/resources.ts`, `docs/art/visual-style-guide.md`, `frontend/src/features/resources/ResourceIcon.tsx`, `frontend/src/assets/resources/README.md`. Перед реализацией сверить каталог заново: он может измениться. Настоящий документ не меняет ассеты и механику.

## Общая визуальная система

Единая ортографическая трехчетвертная камера, прозрачный фон без обязательной плашки, крупный предмет с асимметричным силуэтом и стабильными полями; верхняя и боковая плоскости различимы по светлоте. Теплый основной свет сверху слева, мягкое заполнение справа, короткая контактная тень в альфе. Сохранить характерные материалы Эолии и умеренную насыщенность. Не добавлять текст, мелкие символы и свечение как единственный признак предмета. Редкость показывать формой и материалом, а не общей фиолетовой аурой.

Для твердых материалов — 3–5 крупных видимых граней, неровные сколы и направленный световой акцент; микрорельеф и пятнистость поддерживают форму, но не создают визуальный шум. Для дерева — продольные волокна и контрастный торец; металла — контролируемый блик и следы обработки; ткани — крупное плетение; стекла — толстая кромка и отражение. Текстура должна переживать уменьшение: главная деталь занимает несколько пикселей, мелкие поры лишь дополняют ее. Не полагаться только на цвет для различения соседних ресурсов.

## Размеры и проверка читаемости

Контрольный лист каждого этапа: 16, 20, 22, 24, 30, 32, 34 и 48 CSS px на светлом и темном фоне, при DPR 1 и 2; 16 px особенно важен для встроенных жителей, 20–22 — для карты и стоимости, 30–34 — для обычной и верхней панели. В CSS изображение увеличивается до 1,2, в верхней панели до 1,28: проверить фактические рамки и соседние числа без обрезки и наложения. На мобильной ширине проверить те же поверхности. Сравнить парами камень/блок/глину, древесину/доски, руду/уголь, железо/сталь, веревки, обычные/улучшенные культуры, жидкости и заряды; различие должно сохраняться в оттенках серого. Если деталь исчезает — укрупнить форму или подготовить упрощенную версию, а не усиливать шум.

## Производство и внедрение

1. Инвентаризировать актуальные ID каталога, PNG, GLB и записи `manifest.json`; составить таблицу ID → исходник → runtime-файл → места использования и отметить отсутствия. Отдельно согласовать алиасы `quiet_powder` → `silent_powder`, `plant_oil` → `vegetable_oil`, `oleoresin` → `sap`, `fine_rope` → `rope`, `tile` → `runic_tile`: последние два сейчас разделяют картинку с другим ресурсом, поэтому для отличимых новых иконок нужны собственные файлы и обновление соответствий и тестов. `kaolin` использует отдельный SVG; у `population` по умолчанию inline SVG, а в верхней панели asset. Проверить оба пути и неизвестный ID/fallback.
2. Пилот: камень, блок, древесина, доски, уголь, руда, глина и жители. Утвердить лист фактических размеров в HUD, меню строительства, инспекторе и бейджах карты до массового производства. Затем группы P1 и P2 ниже. На каждый ID — отдельная проверка силуэта и материала; не считать существующие шаблонные формы готовыми.
3. Использовать существующую Blender-сцену и генератор `tools/assets/blender/generate_resource_icons.py`, расширяя `RESOURCES`/`BUILDERS` и специализированные формы по необходимости. Сохранить воспроизводимые исходники, материалы и настройки камеры; PNG 256×256 с альфой, GLB и manifest — по текущему контракту `frontend/src/assets/resources/README.md`. Не перезаписывать вручную результаты fallback-генератора `tools/assets/generate_resource_icon_pngs.py`: он не является целевым качеством. Пересборку производить по группам с проверкой изменений manifest, чтобы не потерять существующие ресурсы.
4. После утверждения PNG выполнить `node frontend/scripts/generate-runtime-resource-icons.mjs` (требуется ImageMagick), проверить полученные WebP и соответствие имен manifest. Поднять `RESOURCE_ICON_ASSET_REVISION` при замене для обновления кэша. Сохранить прозрачность, читаемые поля и фиксированные размеры контейнеров; не менять серверные идентификаторы. Учитывать бюджет runtime и исходников по `frontend/scripts/check-asset-budget.mjs` и правила исключения исходных PNG из поставки.
5. Выполнить `python3 tools/assets/validate_resource_models.py`, соответствующие тесты `ResourceIcon.test.ts`, `ResourceBar.test.tsx`, `npm --prefix frontend run assets:budget` и визуальную проверку в браузере desktop/mobile. Проверить загрузку, прозрачность, fallback, отсутствие 404, корректные подписи и доступность. При изменении исключений обновить тесты и manifest согласованно; отдельно проверить импорт GLB там, где он предусмотрен.

## Объем, приоритеты и приемка

Объем определяется числом актуальных ID, а не числом шаблонов: для каждого нужны модель или авторский исходник, материал, рендер, запись и визуальная проверка. Предварительно три партии: **P0** — пилот и базовые материалы/валюты, наиболее частые в HUD и строительстве; **P1** — остальные сырье, стройматериалы, металлы и производство; **P2** — редкие ресурсы и оружие. Перед каждой партией пересчитать каталог и оценить трудоемкость по итогам пилота; общий срок без пробного производства не фиксировать.

Приемка партии: каждый ID имеет утвержденное уникальное предметное изображение или явно обоснованное общее отображение; характер поверхности и крупные грани соответствуют таблице; пары читаются без цвета на фактических размерах; нет обрезки, артефактов альфы, пропавших файлов и регрессий подписей. Листы сравнения, результаты проверок и перечень исключений сохраняются вместе с изменением. Художественная проверка дополняет автоматический валидатор: он не доказывает узнаваемость материала.

Для отката выпускать каждую партию отдельным коммитом с исходниками, PNG, manifest, runtime WebP и при необходимости изменениями соответствий/ревизии. Откатывать их согласованно целой партией; после отката снова сменить ревизию кэша, проверить оба пути жителей, каолин и алиасы. Не удалять прежние файлы до проверки всех ссылок и доступности новой партии.
