# Инструкция по параллельному выполнению очереди задач

Источник задач: [`queue.txt`](queue.txt). Перед стартом проверь актуальное состояние репозитория и реализацию: очередь могла устареть, а часть работ — уже выполниться. Не дублируй готовую работу. Соблюдай корневой `AGENTS.md`, существующие соглашения и ограничения проекта.

## Общие правила для каждого агента

- Получай только назначенную группу и перечисленные в ней пункты. Не загружай всю очередь и весь план в контекст без необходимости.
- Перед началом каждого пункта найди его строку в `queue.txt` и переключись на модель и уровень усилий, указанные в `(model: ...)`. Не переноси настройку модели от предыдущей задачи: сверяй её заново для каждого пункта, включая подпункты. Если переключить модель невозможно, остановись и сообщи координатору; не подменяй её молча. Используй только перечисленные в очереди разрешённые модели и уровни.
- Перед изменениями кратко проверь относящиеся к задаче файлы, текущую реализацию и незакоммиченные изменения. Не перезаписывай чужие правки.
- Не выходи за назначенную область. Если обнаружена зависимость или конфликт, зафиксируй его и сообщи координатору; независимую часть продолжай.
- Для реализационных задач следуй существующей архитектуре, проверяй все относящиеся к задаче правила на сервере и в клиенте. Документационные задачи сохраняй в указанном месте; Markdown пиши на русском.
- После **каждого отдельного пункта/задачи** закончи ответ кратким отчётом и вызови `/compact`, чтобы освободить контекст перед следующим пунктом. Если интерфейс не поддерживает команду `/compact`, сообщи об этом координатору и продолжи с кратким резюме.
- После выполнения **всей назначенной группы** вызови `$apply-atomic-commits` (скилл `apply-atomic-commits`). Сначала покажи полный упорядоченный план коммитов с файлами/изменениями согласно скиллу; затем создай атомарные Conventional Commits. Не включай чужие изменения, не делай push и не переписывай существующие коммиты.
- В финальном отчёте перечисли пункты очереди, результат, проверки, коммиты и оставшиеся блокеры. Не заявляй о проверках, которые не запускались.

## Рекомендуемый порядок запуска

1. Сначала выполнить короткую сверку очереди с текущим кодом и планом; убрать из раздачи уже закрытые пункты.
2. Планировать максимум **2 одновременно работающих агента**, включая Blender/модельные задачи. Ноутбук с Ryzen 5 5500U и 8 ГБ RAM имеет ограниченный запас памяти: несколько параллельных агентов, браузер/Blender и dev-сервисы могут вызвать своп и замедлить всю работу. При запуске Blender, сборки, контейнеров или нескольких тяжёлых процессов ограничиться одним агентом; второму поручать только лёгкий документальный анализ и не запускать одновременно ресурсоёмкие проверки.
3. Не запускать все группы A, B, E, G, H и I разом. Выбирать максимум две группы с низким пересечением файлов; короткие задачи (например H или отдельный пункт A) удобно ставить рядом с одной крупной задачей. Группы C и D, если затрагивают Blender, выполнять по одной модели/агенту за раз.
4. Группы F и J могут редактировать документы плана. Чтобы избежать конфликтов, согласовать владельца каждого документа; общий `docs/plans/plan.md` в каждый момент редактирует только один агент. Группу J запускать после завершения работ, которые требуют отражения в плане.
5. Если две группы затрагивают одни файлы, назначить одного владельца или запускать их последовательно. До старта сообщить агентам имена общих файлов.
6. После завершения групп интегратор проверяет статус репозитория, результаты и коммиты. Не объединять чужие изменения в коммит без проверки их содержимого.

### Режим работы, учитывающий ноутбук

- Запускай максимум двух агентов одновременно; комфортный режим по умолчанию — один агент на реализацию плюс один на узкую документационную задачу.
- Не запускай одновременно двух агентов, каждый из которых строит/открывает Blender, запускает полный frontend/backend build, контейнерный стек или ресурсоёмкие проверки.
- Если система начинает активно использовать swap, интерфейс тормозит или Blender/сборка конкурирует за память, приостанови запуск новых задач и дождись освобождения ресурсов. Не пытайся компенсировать нехватку RAM увеличением числа агентов.
- Экономь не только вычисления, но и контекст: выдавай агенту одну группу, проси читать только относящиеся к ней файлы и применять `/compact` после каждого пункта, как указано выше.

Пункт 15 в `queue.txt` пустой и не назначается. Нумерацию очереди сохраняй в отчётах, чтобы результаты можно было сверить с исходным списком.
