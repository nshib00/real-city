# План обновления компонентов Real City

Дата аудита: 30 октября 2026 года. Область: frontend, backend, shared, контейнеры, CI, наблюдаемость и инструменты производства ассетов. Это план: зависимости и исходный код приложения при аудите не изменялись.

## Рекомендуемое решение

Обновлять небольшими проверяемыми сериями: сначала воспроизводимость и тесты, затем поддерживаемые runtime и безопасность бэкенда, зависимости приложения, инструменты фронтенда, графика и только затем хранилища. Не совмещать обновление БД, компилятора и рендерера в одном выпуске.

Целевое состояние: Go 1.27 с актуальным исправлением, Node.js 24 LTS как консервативная база либо 26 LTS после проверки совместимости, React 19, Vite 8, Vitest 5, PixiJS 8, Three.js r186. PostgreSQL сначала обновить внутри 16, переход на 18 провести отдельной миграцией; Redis сначала обновить внутри 7, переход на 8 оценить отдельно. TypeScript 7 проверить отдельным экспериментом после сборочного стека. Не менять фреймворки, транспорт и SQL-драйвер ради самого обновления.

## Достоверность и ограничения

Текущие версии npm ниже взяты из `frontend/package-lock.json`, а не из минимальных диапазонов `package.json`. Версии Go — из `backend/go.mod`. Теги контейнеров — из Dockerfile, Compose и интеграционного теста; фактически запущенные версии и digest образов не проверены. Для Python и внешних утилит единый lock-файл не найден.

Целевые релизы сверены с официальными сайтами и репозиториями, ссылки приведены в таблицах. Прямое чтение npm registry из терминала не удалось из-за DNS/сетевых ограничений. Поэтому для части пакетов указана целевая ветка с обязательным уточнением patch перед реализацией; совместимость всей комбинации пока не доказана. GitHub latest в монорепозитории может относиться к другому пакету: например, latest репозитория Vite указывает на create-vite, а не обязательно на vite.

В рабочем дереве есть многочисленные изменения backend, frontend и ассетов. Перед реализацией зафиксировать согласованную исходную точку, не включать чужие изменения в обновления. Полный baseline тестов в рамках подготовки документа не запускался; ниже перечислены обязательные проверки для реализации. Известные уязвимости конкретной сборки без `npm audit`/`govulncheck` здесь не утверждаются.

### Особенности текущей конфигурации

- `@vitejs/plugin-react`, `typescript`, `vite` сейчас находятся в `dependencies`; перенести в `devDependencies`, сохранить runtime-библиотеки в `dependencies`.
- `vite.config.ts` содержит `manualChunks`, `rollupOptions` и собственный `closeBundle` для удаления исходных/резервных ассетов. При переходе на Rolldown проверить поддерживаемый API chunk splitting и порядок выполнения плагинов. Сравнить состав `dist`: нужные GLB/PNG/WebP должны остаться, `.blend`, backup и preview не должны попасть в публикацию.
- `test` находится в Vite-конфиге, импортирующем `defineConfig` из `vite`; при миграции привести типизацию к актуальному Vitest API либо выделить `vitest.config.ts` с общими настройками. Не потерять исключение `tests/e2e/**` из unit-тестов.
- `lint` сейчас означает только `tsc --noEmit`, а `tsconfig.json` включает только `src`. Отдельно проверять конфиги и типы Node; объявить `@types/node` явно под выбранную ветку Node. Не считать имеющуюся команду полноценным ESLint-анализом.
- В `frontend/tests/e2e` есть тесты с `@playwright/test`, но пакет и команда E2E отсутствуют в `package.json`. Добавить закреплённую стабильную версию, конфигурацию `baseURL`/webServer и команду, установить соответствующие браузеры. Версию Playwright и браузеры обновлять вместе. Не считать unit-тесты canvas проверкой реального GPU-рендера.
- `shared/package.json` не содержит внешних зависимостей. Обновлять там нечего; проверить shared API/events/catalog на новой версии TypeScript и согласованность серверных и клиентских контрактов.

## Порядок реализации и критерии завершения

### 0. Воспроизводимость и исходные измерения — P0, 1–2 рабочих дня

Зафиксировать исходный commit и существующие отклонения тестов. Сохранить текущие версии Node/npm/Go/Docker/Compose, `npm ls --depth=0`, граф Go и digest запущенных образов. Сохранить сборку и baseline на одной карте/одном наборе ассетов. Использовать [протокол профилирования](../performance/browser-profiling.md) и [исходные измерения](../performance/observability-baseline.md); старый короткий прогон без игроков не считать эталоном production-нагрузки.

Добавить общий CI для frontend/backend, запускаемый при изменении manifests, lock, исходников и конфигурации. Существующие workflows `audio` и `observability` имеют узкие path-фильтры и не заменяют общий pipeline. Подключить имеющиеся E2E и явно включить контейнерный тест в отдельной job с Docker.

Готово, когда чистый checkout воспроизводимо устанавливается, собирается и проходит оговорённый набор проверок, а исходные сбои записаны отдельно.

### 1. Runtime и бэкенд — P0, 2–4 дня

Обновить Go и builder/runtime образы, затем x/crypto и pq, затем Testcontainers и транзитивный граф отдельными коммитами. Обновить Node/npm синхронно в CI/Compose/локальных настройках. Выполнить tidy новым Go и проверить diff; не смешивать с изменениями игровой логики.

Готово: api, worker и migrate собираются в контейнере; unit/race/vet, реальные PostgreSQL/Redis-тесты и сканирование зависимостей проходят. Устаревшие достижимые уязвимые ветви устранены либо есть обоснованное временное исключение.

### 2. Библиотеки React и состояния — P1, 1–2 дня

Обновить React/DOM/типы вместе, затем Query/Zustand и Testing Library небольшими группами. Lucide вынести в отдельную визуальную проверку. Согласовать нижние границы package.json с выбранными версиями и сохранить lock.

Готово: вход/выход, профиль, меню строительства, инспектор, уведомления, optimistic updates и reconnect работают; нет новых ошибок консоли, утечек подписок и повторных запросов.

### 3. Vite / Vitest / jsdom — P1, 3–5 дней

Пройти миграции Vite 7 и 8 и React-плагина, затем Vitest 3/4/5 и jsdom. Промежуточные версии служат точками диагностики, их не обязательно выпускать. Проверить [руководство Vitest](https://vitest.dev/guide/migration/), требования engines/peerDependencies каждой выбранной версии. Сначала сохранить TS 5.9, чтобы не смешивать ошибки компилятора с изменением сборщика.

Готово: build/test/HMR/API proxy работают, E2E стартуют из чистого checkout, конфиги типизируются. Состав dist корректен; размер JS/ассетов, время загрузки и чанки сравнимы с baseline. Не обходить проблемы `--legacy-peer-deps`, ослаблением strict или отключением тестов.

### 4. Компилятор TypeScript — P1/P2, 1–3 дня

Проверить TS 7 в отдельной ветке после чтения изменений TS 6/7. Убедиться в поддержке текущих CLI-флагов, `tsc -b`, bundler resolution, редактора и типов зависимостей; учитывать нативный компилятор и доступность бинарников на используемых платформах. Проверить shared и инструменты фронтенда. Если исправления непропорциональны пользе, оставить проверенную версию временно, записав конкретные блокеры и дату повторной проверки через месяц.

### 5. PixiJS и Three.js — P1, 2–4 дня

Обновить PixiJS отдельно от Three/types. Проверить PixiStage, terrainTextures, objectTextureCache и 3D-просмотр через BuildingGlbModel. Сравнить обычную карту и сценарии buildings/monsters/mixed на desktop и реальном mobile: zoom/pan/picking, атласы, прозрачность, порядок слоёв, анимации, GLB/LOD, многократное открытие и закрытие просмотра.

Готово: нет пустого canvas и пропавших ассетов; проверено восстановление после переключения вкладки и resize. Предлагаемый порог: ухудшение frame p95, времени загрузки или памяти не более 10% относительно повторяемого baseline; превышение расследуется до выпуска. Это предлагаемый критерий, не измеренный сейчас результат.

### 6. Хранилища — P2, 3–5 дней с репетицией

Сначала обновить patch текущих PostgreSQL/Redis и проверить восстановление backup. Затем отдельно репетировать PostgreSQL 16 → 18 на копии базы с текущими миграциями и репрезентативными данными. Промежуточный переход через 17 не обязателен, но изменения обеих версий прочитать.

Для PostgreSQL 18 проверить [изменение PGDATA и mount point официального образа](https://hub.docker.com/_/postgres): нельзя ограничиться заменой тега и старым mount `/var/lib/postgresql/data`. Подготовить новый volume, использовать dump/restore либо проверенный pg_upgrade, выполнить ANALYZE и сравнить ключевые планы запросов. Обновить одновременно основной Compose, test Compose и строку образа в Testcontainers.

Перед переключением остановить API и все источники записи, включая embedded/standalone simulation worker. Снять финальный backup, проверить число объектов, ownership, ресурсы, очереди действий/outbox и отсутствие двойного тика. На новой базе прогнать migrate status/up и игровые операции. Простой и допустимую потерю данных определить до окна миграции по фактическому объёму базы.

Redis 8 внедрять отдельным выпуском только после проверки RESP, TTL, сессий, idempotency locks и persistence. Не очищать Redis автоматически: потеря idempotency записей может разрешить повторное исполнение действий.

### 7. Наблюдаемость, CI и ассеты — P1/P2, 2–4 дня

Prometheus patch можно выполнить раньше отдельным PR. Grafana major — с backup volume и проверкой provisioning/алертов. Actions обновлять после проверки runner, повторно прогнать обе существующие workflows. Закрепить Python и внешние библиотеки инструментов, выполнить asset/audio smoke. Blender обновлять только после пилота на доме, ратуше, ресурсе и анимированном монстре: сравнить anchor, масштаб, материалы, прозрачность, LOD и обратный импорт GLB. Массовую перегенерацию ассетов в обновление не включать.

Ориентир суммарной трудоёмкости: 15–29 рабочих дней одного разработчика; оценка не включает устранение существующих дефектов, длительное окно миграции большой БД и массовую переделку ассетов. Если нужен быстрый первый результат, этапы 0–2 и patch образов дают основную пользу до дорогих major-миграций.

Команды выполнять из корня, если не указано иное. Сетевые проверки требуют доступа к registry/proxy; версия инструмента сканирования должна быть закреплена в CI.

Для Blender — `make asset-pipeline-blender-roundtrip` в закреплённом окружении. Общие тесты без `TEST_CONTAINERS=1` пропускают найденный контейнерный тест, поэтому зелёного `make test` недостаточно.

При каждом значимом обновлении проверить регистрацию/логин/refresh/logout, строительство и списание ресурсов, повтор одного запроса с idempotency key, конкурирующие действия двух игроков, PvP/PvE, обработку тиков и перезапуск worker, reconnect WebSocket и incremental updates. Метрики HTTP/DB/tick p95, ошибки, WS drops, backlog и память сравнивать на одинаковой нагрузке. Предлагаемый порог деградации p95 — 10%, без новых 5xx и потери игровых событий; утвердить после получения устойчивого baseline.

## Выпуск, откат и сопровождение

Каждая группа — отдельный PR с текущими/целевыми версиями, lock/digest, ссылками на миграции и результатами проверок. В staging запускать одну и ту же сохранённую карту; перед выпуском фиксировать пару версий frontend/backend и совместимость WS/API. Не менять формат событий вместе с обновлением библиотек без необходимости.

Для приложения хранить предыдущие образы и frontend dist; откатить оба при несовместимости. Для PostgreSQL major откат — восстановление старого volume/backup и старых бинарников, а не запуск старого сервера на новом PGDATA. После начала записей в новую БД возврат к старой копии теряет эти записи: до открытия доступа определить процедуру переноса изменений или восстановления. Не использовать down-миграции и `docker compose down -v` как штатный rollback. Grafana откатывать вместе с backup её БД; Redis — по проверенному сценарию восстановления persistence.

Настроить Renovate либо Dependabot для npm, Go, Docker и Actions: patch/minor небольшими группами, major отдельно, графика и хранилища только с ручной проверкой. Еженедельно просматривать обновления безопасности, ежемесячно — остальные; временно отложенные major пересматривать с датой и конкретным блокером. Обновление считается завершённым, когда выбранные версии закреплены, проверки прошли на чистом checkout и staging, восстановление данных отрепетировано, а отложенные компоненты имеют обоснование и срок пересмотра.
