# Рабочий процесс Git

## Цель

Использовать `main` как стабильную интеграционную ветку, а каждую задачу выполнять в отдельной короткоживущей ветке. Изменения попадают в `main` через Pull Request (PR) после проверок CI и ревью. Для этого проекта подходит облегчённый trunk-based процесс; постоянные ветки `develop`, `release` и `hotfix` не нужны, пока команда и процесс выпуска не требуют их отдельно.

## Имена веток и коммитов

Используйте короткие имена веток с типом задачи:

- `feat/map-terrain` — новая возможность;
- `fix/monster-pathing` — исправление;
- `chore/update-dependencies` — обслуживание;
- `docs/git-workflow` — документация.

Коммиты должны описывать одно логически связанное изменение. Рекомендуемый формат сообщения: `тип(область): краткое описание`, например `fix(monsters): корректно обходить край карты`. Большие несвязанные изменения разбивайте на отдельные коммиты, чтобы их было проще проверить и при необходимости отменить.

## Обычный цикл задачи

Начинайте с актуального `main` и создавайте ветку для задачи:

```bash
git switch main
git fetch origin --prune
git pull --ff-only
git switch -c feat/short-task-name
```

Вносите изменения, проверяйте нужные области и коммитьте только файлы задачи:

```bash
git status --short
git add path/to/file
git diff --cached
git commit -m "feat(area): describe the change"
```

Опубликуйте ветку и откройте PR в `main`:

```bash
git push -u origin HEAD
```

В описании PR укажите цель, основные изменения, проверки и известные ограничения. Дождитесь обязательных проверок CI и ревью, затем слейте PR принятой в репозитории кнопкой GitHub. После слияния удалите ветку и обновите локальный `main` перед следующей задачей.

## Правила для `main` и PR

Настройте защиту `main` в GitHub:

- запретите прямой push и force-push;
- требуйте PR для слияния;
- требуйте успешные обязательные CI-проверки;
- включите требование ревью, когда PR проверяет другой участник.

Назначьте обязательными только реально работающие и релевантные CI-проверки. Процесс слияния (обычный merge, squash или rebase) зафиксируйте в настройках репозитория и используйте единообразно. Для небольшой команды или одного автора ревью может быть необязательным; PR и CI всё равно сохраняют проверяемую историю.

Не переписывайте опубликованную общую историю через force-push. Для исправления уже слитого изменения создавайте новую ветку и новый PR.

## Переход с текущего состояния

На момент подготовки инструкции локальный `main` опережает `origin/main` на 64 коммита, а рабочее дерево содержит незакоммиченные изменения. Эти факты сами по себе не показывают, какие коммиты уже опубликованы другими способами или к каким задачам относятся правки. Поэтому сначала проведите инвентаризацию, не сбрасывая и не переписывая историю:

1. Сохраните текущие изменения и составьте список затронутых файлов (`git status --short`). Не используйте `reset --hard`, `clean` или force-push.
2. Обновите сведения об удалённом репозитории (`git fetch origin --prune`) и сравните `main` с `origin/main` (`git log --oneline origin/main..main`, `git log --oneline main..origin/main`).
3. Просмотрите локальные коммиты и выясните, какие из них предназначены для публикации. Не отправляйте все 64 коммита в `main` вслепую: сгруппируйте их по задачам и выберите принятую командой стратегию интеграции через PR.
4. Разберите незакоммиченные правки по задачам. Если они относятся к разным задачам, сохраняйте их отдельно (например, отдельными ветками после безопасного сохранения изменений), чтобы один PR оставался обозримым.
5. После согласованного сохранения нужной работы приведите локальный `main` к принятой базовой версии `origin/main`; только затем начинайте новые задачи по обычному циклу выше.

Если вся локальная история намеренно ведётся только на этой машине, сначала сохраните её в резервной ветке и согласуйте, как представить накопленные изменения в PR. Не меняйте публичную историю и не создавайте PR, содержащий несвязанные задачи.

## Локальные настройки

Опционально включите очистку устаревших ссылок удалённых веток и запрет не-fast-forward обновлений при `pull`:

```bash
git config --local fetch.prune true
git config --local pull.ff only
```

Это настройки только данного клона. Проверьте `.gitignore` на локальные секреты, временные файлы и результаты сборки; не добавляйте личные настройки среды или секреты в коммиты. Не коммитьте автоматически все изменения через `git add -A`, если рабочее дерево содержит файлы нескольких задач.
