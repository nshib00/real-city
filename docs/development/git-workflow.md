# Рабочий процесс Git

## Цель

Использовать `main` как стабильную интеграционную ветку, а каждую задачу выполнять в отдельной короткоживущей ветке. Изменения попадают в `main` через Pull Request (PR) после проверок CI и ревью. Для этого проекта подходит облегчённый trunk-based процесс; постоянные ветки `develop`, `release` и `hotfix` не нужны, пока команда и процесс выпуска не требуют их отдельно.

## Имена веток и коммитов

Используйте короткие имена веток с типом задачи:

- `feat/map-terrain` — новая возможность;
- `fix/monster-pathing` — исправление;
- `chore/update-dependencies` — обслуживание;
- `docs/git-workflow` — документация.

Коммиты должны описывать одно логически связанное изменение в формате Conventional Commits: `тип(область): краткое описание`, например `fix(monsters): корректно обходить край карты`. Большие несвязанные изменения разбивайте на отдельные коммиты, чтобы их было проще проверить и при необходимости отменить.

## Обычный цикл задачи

Начинайте с актуального `main` и создавайте ветку для задачи:

```bash
git switch main
git fetch origin --prune
git pull --ff-only
git switch -c feat/short-task-name
```

Вносите изменения, проверяйте нужные области и коммитьте только файлы задачи:

```bash
git status --short
git add path/to/file
git diff --cached
git commit -m "feat(area): describe the change"
```

Опубликуйте ветку и откройте PR в `main`:

```bash
git push -u origin HEAD
```

В описании PR укажите цель, основные изменения, связанные пункты плана, точные команды проверок и известные ограничения. Не представляйте незапущенные проверки как пройденные; для заметных UI-изменений приложите скриншоты. Дождитесь обязательных проверок CI и ревью, затем слейте PR принятой в репозитории кнопкой GitHub. После слияния удалите ветку и обновите локальный `main` перед следующей задачей.

## Правила для `main` и PR

Настройте защиту `main` в GitHub:

- запретите прямой push и force-push;
- требуйте PR для слияния;
- требуйте успешные обязательные CI-проверки;
- включите требование ревью, когда PR проверяет другой участник.

Назначьте обязательными только реально работающие и релевантные CI-проверки. В этом репозитории есть workflow frontend CI, backend CI, contracts, browser E2E, audio, Docker, observability и production rehearsal; перед выбором правил в GitHub проверьте итоговые имена checks и их актуальность. Процесс слияния (обычный merge, squash или rebase) зафиксируйте в настройках репозитория и используйте единообразно. Для небольшой команды или одного автора ревью может быть необязательным; PR и CI всё равно сохраняют проверяемую историю.

Не переписывайте опубликованную общую историю через force-push. Для исправления уже слитого изменения создавайте новую ветку и новый PR.

## Переход с текущего состояния

Снимок на 2026-11-14: локальный `main` и `origin/main` совпадают на `7a87df4` (расхождение 0/0). В рабочем дереве находятся незакоммиченные изменения приложения и документации. Они сохранены без сброса и остаются несгруппированными по PR. `gh` авторизован как `nshib00`, репозиторий `nshib00/real-city` доступен, открытых PR нет. GitHub API возвращает HTTP 403 при чтении branch protection: для включения этой возможности GitHub предлагает перейти на Pro или сделать репозиторий публичным.

Последние workflow на `main` (`7a87df4`, запуск 2026-11-13) завершились с ошибками: frontend — `npm run assets:budget`, backend — шаг `Format`, contracts — `scripts/check-contracts.sh`, postgres — `Initialize containers`; browser E2E и audio также помечены failed. Эти результаты не подтверждают готовность текущих локальных изменений к PR. Сначала требуется устранить или отдельно классифицировать базовые ошибки CI и проверить точные логи каждого workflow.

Сначала сохраните текущие изменения и составьте список затронутых файлов (`git status --short`). Не используйте `reset --hard`, `clean` или force-push. Перед разделением правок проверьте все diff и определите зависимости между файлами. Текущие предварительные группы: центр справки и связанная интеграция; меню союза; большая кнопка атаки монстра; каталог построек и связанные балансные правки; унификация иконок жителей. Это только ориентир: некоторые файлы содержат hunks из разных задач, их следует разделять точечно.

После безопасного сохранения правок создавайте ветки от актуального `main`, коммитьте только изменения одной задачи, выполняйте релевантные проверки и готовьте отдельный PR для каждой связанной группы. Не отправляйте несвязанные изменения одним PR.

Если локальная история расходится с удалённой, сначала обновите сведения (`git fetch origin --prune`) и сравните ветки (`git log --oneline origin/main..main`, `git log --oneline main..origin/main`). Не отправляйте локальные коммиты в `main` вслепую. Согласуйте стратегию интеграции и не переписывайте публичную историю.

## Локальные настройки

Опционально включите очистку устаревших ссылок удалённых веток и запрет не-fast-forward обновлений при `pull`:

```bash
git config --local fetch.prune true
git config --local pull.ff only
```

Это настройки только данного клона. Проверьте `.gitignore` на локальные секреты, временные файлы и результаты сборки; не добавляйте личные настройки среды или секреты в коммиты. Не коммитьте автоматически все изменения через `git add -A`, если рабочее дерево содержит файлы нескольких задач.
