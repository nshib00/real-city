# Real City Blender Models

Используй этот скилл, когда задача требует создать, изменить или проверить Blender-ассет для Real City. Основной маршрут для production-ассетов: сначала asset spec, общий Blender API, component library и orchestrator; Blender MCP используется для bootstrap, live-инспекции, запуска Blender-side script, viewport/screenshot review и отладки, а не как место для ручного копирования больших скриптов в чат.

## Обязательный контекст

Перед работой в Blender прочитай только релевантные источники. Основной источник правды - asset spec и документация в `docs`, а локальные референсы в `reference/` задают визуальную читаемость и плотность деталей:

- `docs/assets/asset-generation-status.md` - короткая рабочая память по текущим партиям, ограничениям и последним сбоям.
- `docs/assets/specs/**/*.yaml` - production-spec ассета: id, category, levels/states, material map, progression, style/skill profile, LOD policy и PNG policy.
- `docs/assets/specs/schema.json` и `docs/assets/specs/template.yaml` - формат и шаблон нового spec.
- `docs/assets/blender-models-web-pipeline.md` - актуальная factory-архитектура, output contract, LOD/PNG policy, frontend runtime integration.
- `docs/assets/blender-generation-checklist.md` - preview/full gates, style gate, PNG/LOD/manifest checks и короткие рецепты.
- `docs/assets/blender-mcp-troubleshooting.md` - WSL/Windows host, UNC-пути, bootstrap и repair после сбоя.
- `docs/art/visual-style-guide.md` - основной art bible для 3D-ассетов Real City: bright fantasy stylized mid-poly, фирменные эолийские элементы, бюджеты, материалы, состояния и quality gate.
- `docs/visual-style-and-setting-options.md` - Эолия, карта, природа, ресурсы, руины, персонажи, общий визуальный стиль.
- `docs/buildings/` - документация по постройкам по категориям: дома, центр, поля, заводы, дороги, социальные здания и будущие категории.
- `docs/plans/plan.md` - статус ассетов и фаз, если задача связана с планом или очередностью работ.
- `shared/catalog/buildings.ts` - актуальные id, категории, размеры, стоимости, таймеры и цепочки апгрейдов.
- `shared/catalog/resources.ts` - id ресурсов, русские названия и производственные источники.
- `reference/images/` - локальные референсы плотной изометрической карты и читаемости, без копирования IP.
- `reference/buildings/` - распарсенные справочники оригинальной игры; использовать только как анализ категорий, прогрессий, плотности, масштаба и общих приемов читаемости.
- `frontend/public/assets/buildings/` - стандартная runtime-папка новых building assets.
- `frontend/src/assets/` - legacy runtime-ассеты, если модель надо интегрировать в уже существующий src-backed renderer.
- `frontend/src/game/renderers/buildingAssetManifests.ts` и `frontend/src/game/renderers/buildingRegistry.ts` - frontend lookup PNG/GLB по kind, level, state и shape.
- `frontend/public/assets/terrain/tiles/grass.png` - обязательный источник вида единой клетки земли для основания моделей.
- `frontend/public/assets/buildings/center/town_hall/` и `frontend/public/assets/buildings/housing/dugout/` - эталон масштаба runtime PNG для зданий: новые модели должны выглядеть в том же масштабе на карте.

Ищи целевой объект через `rg`, например `rg -n "Землянка|wood_house|нефт|руин|лес" docs shared/catalog reference/buildings`. Не полагайся на память: баланс, названия, описание сеттинга и локальные референсы часто меняются.

Для построек обязательно посмотри подходящие локальные референсы перед моделированием:

- текстовые: релевантный файл в `reference/buildings/`, например `residential.md` для жилья, `factories.md` для заводов, `roads-and-walls.md` для дорог и стен;
- визуальные: 1-3 изображения из `reference/images/` или другой явно указанной пользователем папки `reference/`.

Референсы нужны для общих признаков: изометрическая читаемость, насыщенность цвета, размер деталей, плотность двора, силуэт, отношение здания к тайлу, уровень декоративности. Нельзя переносить из них конкретные названия, персонажей, точные формы, композиции, UI, иконки, изображения или фирменную визуальную идентичность.

Если документация и код расходятся, сначала зафиксируй расхождение в ответе или рабочей заметке, затем используй последнюю явную пользовательскую правку как приоритет. Для runtime-ассета id и цепочка апгрейда должны совпадать с каталогом, если пользователь не просит обновить каталог.

## Быстрый маршрут

1. Определи тип ассета: здание, уровень апгрейда, природа, тайл, ресурсный узел, руина, дорога/стена, поле/урожай, монстр, декор.
2. Прочитай `docs/assets/asset-generation-status.md`, текущий spec или `docs/assets/specs/template.yaml`, затем релевантную документацию из `docs` и при необходимости каталог из `shared/catalog`.
3. Проверь, что spec содержит `style_profile: aeolian_fantasy_midpoly`, `skill_profile`, `material_map`, `lod_policy` и `png_policy`.
4. Для построек прочитай/осмотри релевантные `reference/buildings/` и `reference/images/`; выпиши 3-5 переносимых визуальных принципов без копирования IP.
5. Подключи релевантные локальные Blender skills из `.agents/skills/blender-skills/`: минимум `blender-director`, `genre-strategy-sim`, `fantasy-worlds`, `stylized-style`, `isometric-style`, `hand-painted-style`, `asset-optimization`; добавь `materials`, `texture-workflow`, `lookdev`, `lod-pipeline`, `export-pipeline`, `vegetation-artist`, `environment-artist`, `prop-artist`, `hard-surface`, `creature-artist` или `animation` по типу ассета.
6. Используй component library из `tools/assets/blender/real_city/components/` и общий API из `tools/assets/blender/real_city/`; не дублируй camera/material/export helpers в новом генераторе.
7. Сначала сделай dry-run, затем preview через `tools/assets/generate_blender_asset.py`; full запускай после успешного preview или явного override.
8. Через Blender MCP выполни bootstrap и live quality gate: `get_addon_status()`, `get_scene_info()`, viewport/render/contact-sheet review, затем export/validation.
9. Если MCP, визуальная инспекция или mid-poly качество недоступны, остановись с ошибкой и объясни, что нужно исправить; не выдавай fallback как готовую модель.
10. Сохрани `.blend`, runtime PNG, LOD GLB, manifest/report/contact sheet, обнови frontend registry при новом семействе и `docs/assets/asset-generation-status.md`.
11. Сообщи точные пути, что создано, какие проверки прошли и какие ограничения остались.

## Экономия токенов в длинных сессиях

Для серийной генерации Blender-ассетов не держи всю историю в чате. Поддерживай короткое состояние в `docs/assets/asset-generation-status.md` и обновляй его после крупных партий моделей, изменений правил, staging-результатов и незавершенных проверок.

- Если пользователь просит продолжить генерацию, сначала прочитай `docs/assets/asset-generation-status.md`, затем только релевантные spec/docs/catalog/reference файлы по текущему объекту.
- Не проси пользователя вставлять большие Blender-логи в чат. Проверяй локальные файлы логов сам, например `/tmp/.../blender.log`, и пересказывай только ошибку, итог генерации или последние значимые строки.
- В финальном ответе по ассетам используй короткий формат: что изменено, точные пути, какие проверки прошли, что осталось. Не перепечатывай весь brief, отчеты JSON, списки всех объектов сцены и длинные логи.
- Правила стиля, камеры, construction/damaged, ground и ресурсной читаемости держи в этом `SKILL.md`, а не повторяй в каждом сообщении.
- Для больших наборов сначала делай preview контрольных уровней, обычно низкий/средний/высокий, например 1, 6, 13. Полную генерацию запускай после визуальной и технической проверки preview, если пользователь не попросил сразу весь набор.
- Для повторных итераций формулируй и принимай узкий scope: семейство, уровни, состояния, папка назначения, какие active версии трогать или не трогать.
- Храни подробные художественные brief-файлы в `docs/`, а в чате ссылайся на них: `docs/housing-model-regeneration-brief.md`, `docs/sawmill-housing-style-revision.md`, `docs/resource-model-regeneration.md` и аналогичные.
- При ответах о прогрессе не перечисляй все сгенерированные файлы, если достаточно диапазона вроде `lumber_yard_l01-l13_{active,construction,damaged}.glb/png`.

## Blender MCP

Для фактической работы с Blender читай `references/blender-mcp-procedure.md` и `../../docs/assets/blender-mcp-troubleshooting.md`.

Критично для WSL/Windows: Codex работает в WSL, Blender обычно запущен в Windows. Если MCP-серверу нужен host, используй `172.28.192.1`, а не `127.0.0.1` или `localhost`. Если Blender MCP недоступен, не заявляй, что модель создана; подготовь Blender-ready brief и прямо укажи, что доступ к MCP заблокирован.

Для каждой новой или пересобираемой модели Real City обязательно выполняй этот live quality gate:

1. В начале работы вызови `get_addon_status()` и `get_scene_info()` через Blender MCP.
2. Используй существующие ассеты Real City как стилевой эталон: минимум сравни масштаб, камеру, ground-клетку, плотность деталей и материалы с уже созданными моделями той же категории или ближайшего типа.
3. Создавай художественную mid-poly модель с bevels, объемными материалами, props, читаемой конструктивной логикой и развитием уровней/состояний. Запрещено завершать задачу простыми low-poly примитивами, плоскими рисунками или placeholder-силуэтами.
4. После изменений получи `get_viewport_screenshot()` в изометрическом игровом ракурсе и визуально оцени модель до экспорта. Если screenshot показывает blockout/low-poly качество, исправь модель или остановись с ошибкой.
5. После экспорта проверь `.blend`, `.glb`, PNG/preview, triangle count, размеры, alpha/anchor и manifest/отчет, если они есть в пайплайне.
6. В финальном ответе явно укажи, что MCP-инспекция и screenshot-review выполнены. Если они не выполнены, это не готовая модель.

## Стандарт ассета

Для каждого игрового ассета создай или сохрани:

- исходный `.blend` с чистыми коллекциями;
- runtime-экспорт, обычно `.glb`, если нужен игре;
- имена на базе внутреннего id: `dugout_l01_active`, `dugout_l01_construction`, `dugout_l01_damaged`, `forest_dense_active`, `oil_well_neutral`;
- origin/pivot в центре основания footprint на уровне тайла, если пайплайн не требует иного;
- примененные transforms;
- материалы с понятными именами по роли: `earth_warm`, `grass_bright`, `wood_pale`, `stone_light`, `brick_red`, `metal_worn`, `oil_black`, `water_clear`, `crystal_amethyst`.

## Стиль Real City

- Главная камера - изометрическая стратегия; силуэт должен читаться без подписи.
- Мир Эолии яркий, практичный и сказочно-восстановительный, не мрачный постапокалипсис.
- Геометрия - оптимизированный stylized mid-poly, не primitive low-poly: видимые bevels, объемные фасадные детали, читаемые props, контролируемые triangle budgets и LOD.
- Запрещено выдавать простые low-poly blockout-модели за финальный стиль. `.agents/skills/blender-skills/lowpoly-style` можно использовать только для дальних LOD, collision/proxy или временного blockout, но не как art direction.
- Основные style skills для Real City: `.agents/skills/blender-skills/fantasy-worlds`, `.agents/skills/blender-skills/stylized-style`, `.agents/skills/blender-skills/isometric-style`, `.agents/skills/blender-skills/asset-optimization`; для планирования - `.agents/skills/blender-skills/blender-director`.
- Каждый уровень постройки выглядит как апгрейд предыдущего, а не только как перекраска.
- У каждой модели должна быть единая клетка земли, визуально взятая и переиспользованная из `frontend/public/assets/terrain/tiles/grass.png`: тот же плоский ромбический footprint, цветовая гамма травы, мягкие вариации покрытия и читаемый изометрический край. Цвет и освещение ground-клетки должны совпадать с `frontend/public/assets/terrain/tiles/grass.png` и пайплайном terrain/grass, а не с локально подобранной более темной/светлой подложкой. Для построек эта клетка земли должна быть плоской на уровне terrain, без выпирающих бугров, поднятых платформ, толстых подставок или декоративных бортиков, которые делают ассет выше соседних клеток карты. Объем здания, props, обломки, растения и тени могут подниматься над клеткой; сама земля остается ровной базовой плоскостью.
- Масштаб runtime PNG должен быть единым для всех моделей одного игрового слоя. Для зданий ориентируйся на текущие PNG ратуш и землянок как эталон: те же камера, ортографический масштаб, размер кадра, anchor и видимая ширина ground-клетки. Другие здания, производства, поля, стены и декор не должны становиться визуально крупнее или мельче из-за отдельной подгонки камеры под силуэт; меняется только реальный footprint/высота модели, а не общий пиксельный масштаб мира.
- Клетка земли у `construction` и `damaged` должна совпадать с `active` того же уровня: геометрия грунта и покрытия, дорожки, размеры, высота, положение, материалы и UV. Копируй основание из active без независимой генерации, перекраски, обугливания или центрирования по изменившемуся силуэту. Разрушать можно здание, но не клетку; строительные материалы и обломки добавляй отдельными объектами. Для PNG сохраняй камеру, масштаб, anchor, освещение и цветовой профиль active; естественные различия теней от здания допустимы. Перед экспортом сравни основание состояний, после экспорта проверь его геометрию и материалы в GLB и совмещение клетки на рендерах.
- Все детали, которые по смыслу стоят на земле, фундаменте, грядке, полу или раме, должны физически касаться этой опоры нижней гранью/основанием. Нельзя оставлять столбы, стены, рейки, бревна, станки, мешки, камни, подпорки, обломки и props левитирующими даже на небольшой зазор; если нужна высота, добавь явную опору.
- Стены, ограды, бортики, рамы и дорожные/стенные сегменты должны соединяться между собой без пустых пробелов между столбами, бревнами, рейками, каменными блоками или панелями. Допустимы декоративные швы и небольшие фаски, но не разрывы, через которые видно фон/землю там, где конструкция должна быть цельной.
- Стройка показывает незавершенное здание: частично возведенные стены, открытые балки и стропила, недостающие участки кровли и еще не установленные окна. Леса и материалы дополняют эту геометрию. Полностью готовое здание с одними лесами не считается construction-вариантом. Минимальный критерий: должно отсутствовать или быть неустановленным примерно 30-60% финальной надземной конструкции, включая часть крыши или стен; должен быть виден строительный порядок от основания и каркаса к стенам, крыше и отделке. Для ранних уровней допустим проще каркас, для поздних - больше стадийных подсборок, материалов и временных креплений.
- Поврежденная версия заметно разрушена уже в игровом масштабе: крупные реальные проломы, утраченные или обрушенные части крыши и стен, сломанные опоры, обломки материалов на земле. Одних темных пятен, мелких трещин или изменения цвета недостаточно. Минимальный критерий: должно быть потеряно, обрушено или явно сломано примерно 35-65% уязвимых верхних элементов, включая крышу, стены, опоры, производственные узлы или декоративную надстройку. Сохраняй узнаваемые признаки типа здания, но не обязательно целый первоначальный силуэт.
- В construction и damaged не должно быть висящих в воздухе деталей: обрезанные стены, крыша, балки, леса, станки и обломки обязаны иметь читаемую опору на землю, фундамент, стойки, соседние стены, стропила или завал. Если при сечении/разрушении остается изолированный кусок без опоры, удали его, добавь подпорку или перемести как обломок на землю.
- До моделирования сопоставь материальные ресурсы стоимости текущего уровня и предыдущих апгрейдов с видимыми частями здания. Доски должны читаться как дощатая конструкция, каменные блоки как кладка, сталь как крепления или силовой каркас, ветролист как крупные плотные зеленые листья. Все такие ресурсы должны быть представлены в модели, а не только ящиками рядом. Монеты и другие нематериальные затраты не требуют буквального изображения. Плотность или роль нового материала должна усиливать читаемость апгрейда.
- Эолийские кристаллы - вытянутые тонкие шестиугольные кристаллы аметистового цвета; использовать редко, только для премиумных, руинных, магико-технических или явно описанных объектов.
- Нельзя копировать Gnomgrad: названия, персонажей, точные формы объектов, UI, иконки, изображения и тексты.
- Локальные референсы из `reference/` использовать как направление качества: яркая изометрия, читаемый силуэт, крупные детали, плотная карта, но все игровые формы и материалы должны оставаться оригинальными для Real City.

## Единые правила генерации моделей

Применяй эти правила ко всем новым и пересобираемым моделям Real City, если пользователь не задал более конкретные требования.

- Изометрия и runtime PNG: основная проверка читаемости идет в игровом изометрическом ракурсе. Для серий одного семейства сохраняй одинаковые камеру, масштаб, освещение, цветовой профиль и anchor, чтобы уровни не прыгали на карте.
- Единый PNG-масштаб: для building/runtime PNG используй ратуши и землянки как эталон масштаба карты. Базовый ориентир текущего пайплайна: кадр `512x384`, anchor `[256, 292]`, видимая ширина ground-клетки около `278 px`, если конкретный валидатор или manifest не задает более точные значения. Запрещено увеличивать/уменьшать ортографическую камеру отдельно для нового семейства, чтобы оно "лучше заполнило кадр"; новый ассет должен совпадать с эталоном по пиксельному размеру клетки и пропорциям относительно соседних моделей.
- Силуэт уровня: каждый следующий уровень должен показывать реальный апгрейд формы, объема, материалов и производственных/жилых деталей. Простая перекраска, добавление одного prop или изменение размера без новых конструктивных признаков не считается апгрейдом.
- Материалы из стоимости: до моделирования сопоставь ресурсы уровня и предыдущих апгрейдов с видимыми частями. Доски показывай как настил, стены, балки или штабеля; каменные блоки - как кладку, цоколь, фундамент или опоры; сталь - как крепеж, рамы, механизмы или усиления; ветролист - как плотные крупные зеленые листья на конструкции; редкие магико-технические ресурсы - как умеренные акценты. Ресурсы должны присутствовать в самой модели, а не только в ящиках рядом. В отчете или generation notes фиксируй краткую карту `ресурс -> видимая деталь`, особенно для новых материалов апгрейда.
- Единая клетка земли: каждая модель получает базовую ground-клетку, переиспользующую `frontend/public/assets/terrain/tiles/grass.png`. Для построек ground должен быть плоским, находиться на уровне terrain и не выглядеть как отдельная выпирающая подложка рядом с обычными клетками карты. Цвет, яркость, насыщенность, направление света, сила теней, world/background light, view transform и render engine для ground-клетки должны совпадать с terrain/grass; если модель рендерится отдельным скриптом, сначала перенеси в него terrain camera/light setup или общий helper, затем уже добавляй объект. Не создавай для нового семейства отдельную травяную подложку с другим масштабом, цветом, высотой, формой или освещением, если пользователь явно не меняет terrain style guide.
- Active основание: земляная клетка, дорожки, покрытие и footprint задают опору для всех состояний уровня.
- Construction основание: копируй ground из active того же уровня без независимой генерации, изменения материалов, UV, положения, высоты или размера.
- Damaged основание: копируй ground из active того же уровня без обугливания, перекраски, дыр, сдвига или центрирования по разрушенному силуэту. Обломки добавляй отдельными объектами поверх земли.
- Опора деталей: у active, construction и damaged не должно быть висящих в воздухе стен, крыш, балок, лесов, механизмов или обломков. Каждая крупная деталь должна геометрически и визуально опираться на землю, фундамент, стойку, стену, стропило, соседний завал или другую понятную конструкцию; перед экспортом проверь нижние грани/минимальный Z у стоящих деталей.
- Соединение конструкций: у стен, оград, бортиков, рам, мостков, дорог и модульных сегментов соседние части должны касаться или слегка перекрываться. Столбы не должны стоять отдельно от бревен/панелей, если это не специальный разрушенный или construction-вариант с явно показанным недостроем.
- Геометрия и экспорт: применяй transforms, проверяй нормали, не оставляй не-манихолдные разрывы у финальных закрытых деталей, держи triangle budget из art bible и локального brief, сохраняй `.blend` и runtime `.glb/.png` по id семейства.
- Проверка после генерации: сравни active/construction/damaged на одинаковом рендере, проверь ground-сигнатуру, PNG-размер, визуальный anchor и масштаб относительно эталонных PNG ратуш/землянок, затем прогоняй профильный валидатор, если он есть.
